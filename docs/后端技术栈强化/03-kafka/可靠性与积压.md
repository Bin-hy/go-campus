# 消息不丢、不重、不乱序，还积压了怎么办？—— 可靠性与积压

> 属于 S3 Kafka 深入 · 第三篇
> 上一篇：[生产消费语义](./生产消费语义)　下一篇：[面试题集](./面试题集)

前面讲了生产者、消费者各自的语义。这一篇把"不丢、不重、顺序"拼成完整方案，再处理线上最头疼的"消息积压"。

## 不丢：三段都要设防

消息从生产到消费要经过"生产者 → Broker → 消费者"三段，任何一段疏忽都可能丢。

- **生产端**：`acks=-1`（所有 ISR 副本确认）+ `retries>0`（失败重试）+ `min.insync.replicas>=2`（防止 ISR 只剩 Leader 时 -1 退化成 1）。
- **Broker 端**：副本数 >=3，`unclean.leader.election.enable=false`（宁可不选落后副本当 Leader，也不丢数据）。
- **消费端**：**手动提交 offset**，且"先处理业务、再提交"（at-least-once）。

## 不重：靠消费端幂等

at-least-once 语义下，重复是常态，别指望"让消息恰好只投递一次"，而是**让重复消费的结果幂等**。三种常见手段：

1. **唯一键/唯一索引**：消息带业务唯一 ID，落库时靠唯一索引去重。
2. **去重表**：消费前查去重表，已处理就跳过。
3. **状态机**：更新前校验状态（订单只能从"待支付"变"已支付"一次）。

## 顺序：只保证单分区有序

Kafka **只保证单个分区内有序**，不保证跨分区有序。要保证顺序，本质是"让需要有序的消息进同一个分区"：

- 全局有序 → 单分区（牺牲并行，吞吐低）
- **同 key 有序** → 按 key 哈希到同一分区（最常用，如同一订单的消息都进同一分区）

消费端还要注意：一个分区只被一个消费者消费，且**分区内要串行处理**（每分区一个处理协程），否则多线程处理会乱序。

## 积压：消息追不上了

消息积压的典型表现是消费组的 **lag**（落后量）持续增大。原因不外乎：消费者实例太少、消费逻辑太慢、频繁 rebalance、流量洪峰。

处理步骤：先看 lag 定位 → **临时扩容消费者**（但上限是分区数，超过也没用）→ 优化消费逻辑（批量、异步）→ 极端情况用"临时新 topic 转储积压消息，用大量消费者并行消化再回写"。

长期看，要增加分区、优化下游、评估容量。记住那个关键约束：**消费者扩容上限 = 分区数**。

---

## 串起来

可靠性的三件事——不丢（三段设防）、不重（幂等消化）、顺序（同 key 同分区 + 分区串行）——拼起来就是一条可靠的链路；积压是这条链路超载的信号，要按"定位 → 扩容 → 优化 → 兜底"的顺序处理。
