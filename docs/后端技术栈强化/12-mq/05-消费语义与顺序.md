# 消费语义与顺序：消费组、位点与重复消费

> 专题第 5 篇 · 上一篇：[可靠性对照](./04-可靠性对照) · 下一篇：[能力边界](./06-能力边界)
> 目标：把「谁消费、消费到哪、怎么并行、顺序怎么保证」四个问题一次讲清。

## 一、两种消费驱动：拉与推

| | Kafka：拉（pull） | RabbitMQ：推（push） |
|---|---|---|
| 谁发起 | 消费者主动 `poll` | Broker 主动投递 |
| 节奏控制 | 消费者决定一次拉多少、多久拉一次 | Broker 按 prefetch 控制在途量 |
| 空转 | 长轮询等待（`fetch.max.wait.ms`） | 无消息时不投递，无空转 |
| 背压 | 天然：处理慢就少拉 | 靠 prefetch 与 credit 流控 |
| 延迟 | 受攒批/长轮询影响，毫秒~几十毫秒 | 通常更低，亚毫秒~毫秒 |

**Q：Kafka 为什么不用推？推不是延迟更低吗？**

因为 Kafka 的核心场景是「多消费组、各自速度不同、还要能批量回放」。Broker 无法同时适配所有组的速度：推快了压垮慢组，推慢了拖累快组。拉模型把节奏交给消费者，天然支持背压和批量。代价是「没数据时可能空转」，用长轮询解决。

**Q：RabbitMQ 的推不怕压垮消费者吗？**

靠 prefetch。消费者声明「我最多同时持有 N 条未确认消息」，Broker 达到上限就停推。所以 **prefetch 是 RabbitMQ 消费侧最重要的参数**，没有它，消费者会被瞬间灌满。

## 二、Kafka 消费组：把「分活」做成协议

### 2.1 四个位置概念，别混

| 名称 | 含义 | 谁维护 |
|------|------|--------|
| **position** | 消费者下一次 fetch 的位置（内存） | 客户端 |
| **committed offset** | 已提交的消费进度 | 存 `__consumer_offsets` |
| **log end offset (LEO)** | 分区最新末尾 | Broker |
| **lag** | `LEO - committed offset` | 监控计算 |

**Q：重启后从哪继续？**

从 **committed offset** 继续。如果这个组从没提交过（新组），由 `auto.offset.reset` 决定：`earliest`（从头）或 `latest`（从最新）。如果提交的 offset 已经过期被删（`OffsetOutOfRange`），同样走这个配置。

### 2.2 一次 poll 背后发生了什么

```text
poll(timeout)
 ├─ 确保已加入组（必要时 JoinGroup / SyncGroup）
 ├─ 发 Fetch 请求给各分区 Leader（长轮询最多等 fetch.max.wait.ms）
 ├─ 返回最多 max.poll.records 条（默认 500）
 ├─ 心跳线程独立发送 Heartbeat（heartbeat.interval.ms）
 └─ 若两次 poll 间隔 > max.poll.interval.ms → 被踢出组 → rebalance
```

这解释了一个经典故障：**消费逻辑里做了 5 分钟的全量计算**，超过 `max.poll.interval.ms`（默认 5 分钟），消费者被判定死亡，分区被分给别人，自己回来后又触发 rebalance，来回抖动。解法：调大该参数，或减小 `max.poll.records`，或把重活丢给线程池（注意提交语义）。

### 2.3 提交粒度：整批还是逐条

| 方式 | 崩溃后的重放量 | 吞吐 | 建议 |
|------|----------------|------|------|
| 整批处理完提交 | 整批 | 高 | 批处理可重放时用 |
| 逐条处理逐条提交 | 1 条 | 低（同步提交往返） | 强实时、单条昂贵时用 |
| 周期性异步提交 | 不确定（可能重复一批） | 最高 | 必须幂等 |

**Q：异步提交会不会丢位点？**

会丢「最后一次提交」，导致重复消费，但**不会跳过消息**（位点只会前进）。所以 at-least-once 场景可以接受。

### 2.4 Rebalance 带来的重复

rebalance 时，分区从消费者 A 移到 B。A 可能已经处理了一部分但还没提交，B 从旧位点开始 → 重复。这是**结构性重复**，不可能靠调参消除，只能靠幂等。

## 三、RabbitMQ 的「消费组」：没有组，只有竞争

**Q：RabbitMQ 有消费组吗？**

没有 Kafka 那种「组 + 位点」的概念。它的模型是：

- **同一队列上的多个消费者 = 竞争消费**（competing consumers）：消息轮询派发，每条只给一个消费者；
- **想要多个下游各自消费全量 = 多个队列绑定同一 Exchange**，消息在 Broker 内复制；
- **消费进度 = 未确认消息集合**（unacked），没有「位点」可回退。

对照一下：

| 需求 | Kafka | RabbitMQ |
|------|-------|----------|
| 一个下游内部并行 | 同组多消费者，分区瓜分 | 同队列多消费者，消息瓜分 |
| 多个下游各自全量 | 多个消费组，共享一份日志 | 多个队列，各存一份消息 |
| 断点续传 | 提交 offset，可回到任意位置 | 未 ack 的消息自动回到 ready；已 ack 的没了 |
| 回放历史 | 支持 | 不支持 |

**Q：RabbitMQ 怎么保证「同一订单的消息不被两个消费者同时处理」？**

默认不保证——消息是逐条派发的。需要业务自己保证：

- 按订单号哈希到固定队列（consistent-hash exchange），每个队列单消费者；
- 或用 **Single Active Consumer**：同一队列同时只有一个消费者活跃；
- 或在消费端用分布式锁按订单号串行化。

## 四、顺序性：承诺到哪，什么会破坏它

### 4.1 Kafka：分区内有序

```text
Producer(key=orderId) → 同一 key 进同一分区 → 分区内追加有序 → 单消费者顺序处理
```

破坏顺序的四个原因：

1. 增加分区数，同 key 映射变化；
2. 生产者重试 + 未开幂等 + `max.in.flight > 1`；
3. 消费端把同一分区的消息丢进线程池并发处理；
4. 失败消息跳到重试 Topic 后，与原分区的新消息交叉。

第四条最容易被忽略：**重试机制天然破坏顺序**。要保序，失败时应该**阻塞该分区**（不提交、不跳过），而不是绕道重试队列。

### 4.2 RabbitMQ：单队列 + 单消费者

- 多消费者 → 并发处理 → 完成顺序不可控；
- `nack(requeue=true)` → 消息回队列，顺序变化；
- 优先级队列 → 本来就不保证 FIFO。

要顺序：单队列单消费者、SAC，或按 key 拆队列。

### 4.3 顺序与吞吐的选择

| 要求 | 方案 | 代价 |
|------|------|------|
| 同 key 有序 | Kafka 按 key 分区 / RabbitMQ 按 key 拆队列 | 热点 key 打爆单分区 |
| 全局有序 | 单分区 / 单队列单消费者 | 吞吐退化为单通道 |
| 尽量有序 + 高吞吐 | 允许乱序，业务侧按版本号/状态机纠偏 | 逻辑复杂 |

**Q：电商订单场景，到底要不要全局有序？**

多数时候不需要。需要的是「同一订单的事件有序」，不同订单之间互不关心。用订单号做 key 即可。真正的全局有序往往意味着设计有问题——先问「为什么需要全局顺序」。

## 五、并行消费的正确姿势（Go 示例）

### 5.1 Kafka：分区级并行

```go
// kafka-go：一个 Reader 内部已按分区并行拉取；
// 若要业务侧并发，按 key 分片到固定 worker，保证同 key 串行
workers := make([]chan kafka.Message, 8)
for i := range workers {
    workers[i] = make(chan kafka.Message, 100)
    go func(in <-chan kafka.Message) {
        for m := range in { handle(m) }
    }(workers[i])
}
for {
    m, err := r.FetchMessage(ctx)
    if err != nil { break }
    idx := int(crc32.ChecksumIEEE(m.Key)) % len(workers)
    workers[idx] <- m          // 同 key 固定 worker → 局部有序
    r.CommitMessages(ctx, m)   // 注意：此处提交早于处理完成，仅作示意
}
```

最后一行是**反面教材**：先提交再异步处理 = at-most-once。正确做法是 worker 处理成功后回报，再按「最小未完成 offset」提交，或干脆整批同步处理。

### 5.2 RabbitMQ：prefetch + 手动 ack

```go
ch.Qos(20, 0, false)  // 每个消费者最多 20 条未确认
msgs, _ := ch.Consume(q, "", false, false, false, false, nil)
for d := range msgs {
    if handle(d.Body) == nil {
        d.Ack(false)
    } else if retries(d) < 3 {
        d.Nack(false, false)  // 不重回原队列，交给 DLX 做延迟重试
    } else {
        d.Nack(false, false)  // 进死信，人工处理
    }
}
```

## 六、重复消费的系统性治理

重复的来源不止一种：

| 来源 | 说明 |
|------|------|
| 消费端崩溃 | 处理完未提交/未 ack |
| rebalance | 分区迁移，新消费者从旧位点开始 |
| 生产端重试 | 未开幂等，Broker 已写入但 ack 丢失 |
| 网络分区 | 消费者以为失败，实际成功 |

治理顺序：

1. **能幂等就幂等**：唯一键、状态机、版本号；
2. **缩小重复窗口**：合理提交粒度 + 幂等生产者；
3. **可观测**：记录消息 ID、消费次数、重复率；
4. **兜底对账**：定时比对业务状态与消息流水。

**Q：幂等和去重表会不会成为新瓶颈？**

会。去重表写放大、Redis 热点都可能成为瓶颈。所以要按业务选粒度：订单级去重（量小）优于消息级去重（量大）；能用状态机判断的，不要额外建表。
