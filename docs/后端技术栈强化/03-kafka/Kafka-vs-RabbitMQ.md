# Kafka vs RabbitMQ：一场从"为什么"开始的追问

> 定位：消息队列选型的入门到深水区，全文用「初学者提问 → 解释 → 再追问」的方式推进。
> 前置阅读：[Kafka 架构与存储](./架构与存储)、[生产消费语义](./生产消费语义)
> 相关落地：[Kafka 削峰与可靠投递](../../架构师修炼/05-Kafka削峰与可靠投递落地)

很多人面试被问"Kafka 和 RabbitMQ 有什么区别"，能背出"一个吞吐高、一个延迟低"就算过关。但这只是结论，不是理解。真正的分水岭在于：**两者的数据模型不同，而数据模型决定了它们能做什么、不能做什么。** 这篇文章从一个什么都不懂的新手开始，一层层往下问。

---

## 第一层：消息队列到底解决什么问题？

### Q1：我直接调接口不行吗，为什么要中间加一个"队列"？

假设下单成功后要做四件事：扣库存、发短信、加积分、写审计日志。最直接的做法是下单接口里顺序调用四个服务：

```text
用户请求 → 订单服务 → 扣库存(50ms) → 发短信(200ms) → 加积分(30ms) → 写日志(20ms) → 返回
```

问题有三个：

1. **慢**：用户要等 300ms，其中发短信的 200ms 跟"下单成功"毫无关系。
2. **脆**：短信服务挂了，整条下单链路跟着失败——可短信失败关下单什么事？
3. **扛不住峰值**：秒杀时 1 万请求同时打进来，库存服务被打穿。

消息队列就是在这三处下手：

- **异步**：下单只写一条消息就返回，短信慢慢发。用户感知从 300ms 降到 10ms。
- **解耦**：短信服务挂了，消息堆在队列里，等它恢复再消费。下单不受影响。
- **削峰**：1 万请求先落队列，下游按自己的能力（比如每秒 500）慢慢消费，队列当缓冲池。

所以消息队列的本质不是"传消息"，而是**把"必须现在做"变成"可以稍后做"，把"强依赖"变成"弱依赖"**。

### Q2：那它和"数据库存一张任务表 + 定时扫表"有什么区别？

初学者常问这个，因为两者看起来都是"先记下来，回头再处理"。区别在于：

- 扫表是**轮询**，有延迟、有无效查询、还要自己处理并发抢占（多台机器扫同一张表会重复处理）；
- 消息队列是**事件驱动**，消息一到立刻推送/被拉走，天然支持多消费者、重试、死信。

不过这个对比也埋下了伏笔：后面你会看到，**RabbitMQ 更接近"任务表 + 精准派发"，Kafka 更接近"一份只追加的流水账"**。两者的"性格"从这里就开始分岔了。

## 第二层：两者的消息模型，到底差在哪？

### Q3：都说 RabbitMQ 是"队列"，Kafka 是"日志"，这两个词有什么区别？

先看 RabbitMQ 的模型：

```text
Producer → Exchange --(Binding + RoutingKey)--> Queue → Consumer
                  ↘ 另一个 Queue → 另一个 Consumer
```

生产者**不直接发到队列**，而是发给 **Exchange（交换机）**，Exchange 按规则（Binding）把消息复制/路由到一个或多个 Queue，消费者从 Queue 里取。

再看 Kafka 的模型：

```text
Producer → Topic(Partition 0, Partition 1, ...) ← 只追加写
Consumer Group A 读 Partition 0/1（各自记录 offset）
Consumer Group B 也读 Partition 0/1（另一套 offset，互不影响）
```

Kafka 里没有"队列"这个会被消费清空的东西。Topic 是一份**按分区组织的、只追加的日志文件**，消息写进去后**不会因为被消费而删除**，只按时间或大小过期（或 compact）。

### Q4：这个区别听起来很抽象，能不能用生活场景讲？

可以，用两个场景：

**RabbitMQ ≈ 快递驿站。** 快递员（生产者）把包裹交给驿站（Exchange），驿站按地址（RoutingKey）分拣到不同货架（Queue），你（消费者）取走一个，货架上就少一个。**包裹被取走就没了**，没取走的会一直占着货架。如果你想让三个人都收到同一份通知，得让驿站复印三份放到三个货架。

**Kafka ≈ 电视台 / 报纸合订本。** 节目（消息）照常播出、报纸按期装订，**谁看谁不看，电视台不关心**。每个观众自己记"我看到第几页了"（offset）。你想回看上周的节目？可以，带子还在（保留期内）。三个人想看同一个节目？各自看各自的，互不影响。

这个比喻能推出后面几乎所有差异：

| 现象 | 驿站（RabbitMQ） | 电视/合订本（Kafka） |
|------|------------------|----------------------|
| 消费后消息还在吗 | 不在，被取走 | 在，到期才删 |
| 能回看历史消息吗 | 不能 | 能，seek 到任意 offset |
| 多人看同一条 | 要复制多份 | 天然支持（多个消费组） |
| 堆积多了会怎样 | 货架堆满，压力大 | 就是多写几页纸，正常 |
| 能按复杂规则分拣吗 | 强项（四种 Exchange） | 弱，只有 Topic 分区 |

### Q5：为什么 RabbitMQ 要设计 Exchange 这一层，直接发队列不行吗？

因为**"消息发给谁"和"消息存在哪"是两个问题**。Exchange 让你把"路由规则"从生产者手里拿出来：

- **direct**：RoutingKey 完全匹配，比如 `order.created` 只进 `order.queue`；
- **fanout**：广播，忽略 RoutingKey，所有绑定的队列都收到一份；
- **topic**：通配符匹配，`order.*.created` 能匹配 `order.pay.created`；
- **headers**：按消息头属性匹配，用得少。

好处是：生产者只管发 `order.created`，**新增一个下游（比如风控）只要去绑定一下，生产者代码一行不改**。这是 RabbitMQ 在"业务事件分发"场景的核心竞争力。

### Q6：那 Kafka 为什么不学它？

因为 Kafka 的出生目的就不是"业务消息分发"。它 2011 年在 LinkedIn 诞生，解决的是**日志聚合**：成千上万台机器的访问日志、监控指标要汇到一个地方，再喂给离线/实时计算。这个场景要的是：

- **极高的写入吞吐**（日志量巨大）；
- **数据能被多个下游重复读**（实时计算读一遍、离线仓库读一遍、审计再读一遍）；
- **能回放历史**（算错了要重跑）。

要做到"多个下游各自读全量"，最自然的模型就是"一份日志 + 各自记 offset"，而不是"给每个下游复制一份消息"。**路由能力被牺牲了，换来的是吞吐、解耦和可回放。** 这是典型的架构取舍，不是谁比谁先进。

> 一句话记住：**RabbitMQ 是"消息路由器"，Kafka 是"分布式提交日志"。** 前者关心"这条消息该给谁"，后者关心"这条消息如何被高吞吐地持久记录并被多方消费"。

## 第三层：吞吐与存储，差距从哪来？

### Q7：Kafka 号称百万级吞吐，RabbitMQ 只有几万，差了两个数量级，凭什么？

先别急着背"顺序写 + 零拷贝"，那是**单机写读快**的原因，吞吐差距还有另外两层：**批处理**和**并行模型**。拆成四根支柱看：

**① 顺序写。** Kafka 只往分区文件末尾追加，磁盘磁头几乎不移动。随机写要寻道，顺序写接近内存速度。

**② 页缓存 + 零拷贝。** 写入先落 OS Page Cache 异步刷盘；消费时用 `sendfile` 让数据从页缓存直接到网卡，绕过用户态，省掉两次拷贝和两次上下文切换。

**③ 批量。** 生产者端攒批（`batch.size` / `linger.ms`），压缩后一次网络请求发一大批；Broker 端一次落盘一大段；消费端一次拉一批（`fetch.min.bytes` / `max.partition.fetch.bytes`）。**摊薄了每条消息的固定开销**（系统调用、网络包、索引更新）。

**④ 无状态消费 + 分区并行。** Kafka 的 broker 不记录"这条消息谁消费了没有"，消费进度由客户端提交到 `__consumer_offsets`。broker 只负责"按 offset 读文件"，是一条**几乎无锁的读路径**。而 RabbitMQ 每个队列都要维护消息状态、投递记录、ack 状态、prefetch 计数，还要处理"推给谁、多久没 ack 要重投"，这些**状态管理是有成本的**，而且一个队列的消息处理天然难以横向并行。

### Q8：RabbitMQ 就不能批量、不能并行吗？

能，但受模型限制：

- **批量的边界是"一条消息"**：AMQP 协议层面没有 Kafka 那种"一批消息一个批次"的概念，confirm 也是逐条（或按批次确认，但生产端仍是逐条投递）。
- **并行的边界是队列**：一个队列可以被多个消费者竞争消费，但消息在队列里是**一条条出队**的，队列本身是单点。想并行只能拆多个队列，而队列一多，Erlang 进程和内存开销就上来了。
- **推模型要做流控**：broker 主动推，必须靠 `basic.qos(prefetch)` 限制在途消息数，否则消费者被压垮。流控本身就是开销。

所以 RabbitMQ 的定位是**低延迟、中等吞吐的业务消息**：单队列几万 QPS 很轻松，延迟常在亚毫秒到几毫秒；Kafka 单分区几十万、集群百万级，但端到端延迟受攒批影响，常在几毫秒到几十毫秒。

### Q9：等一下，Kafka 把消息写磁盘，怎么会比 RabbitMQ 快？磁盘不是很慢吗？

这是最经典的误解。三个原因：

1. **"写磁盘"不等于"同步落盘"**。Kafka 默认 `acks=all` 也只要求写入页缓存 + 所有 ISR 副本的内存，**并不强制 fsync**。真正的持久化交给 OS 异步刷盘。你以为在等磁盘，其实在等内存。
2. **顺序写的磁盘不慢**。机械盘顺序写能到几百 MB/s，SSD 更高，且没有寻道。Kafka 的写是纯追加，**一条消息只写一次**。
3. **读路径几乎不碰用户态**。零拷贝让"读文件发给消费者"变成内核内部搬运。

反过来，RabbitMQ 的消息在内存里做路由、入队、投递、等 ack，**每条消息的状态变更都伴随锁和进程调度**；持久化消息还要写磁盘（虽然也走批量刷盘）。在"海量小消息"这个维度上，状态管理成本压过了 IO 成本。

### Q10：那 Kafka 的消息存在哪？磁盘会不会被写满？

每个分区在磁盘上是一个目录，里面切成多个 **Segment（段文件）**：

```text
order-topic-0/
├── 00000000000000000000.log      # 消息本体
├── 00000000000000000000.index    # offset → 物理位置 的稀疏索引
├── 00000000000000000000.timeindex# 时间戳 → offset
├── 00000000000000036800.log      # 写满 1GB（segment.bytes）就滚动新段
└── ...
```

清理有两种策略：

- **delete（默认）**：按时间（`retention.ms`，默认 7 天）或大小（`retention.bytes`）删除旧 segment。**整段删，不逐条删**，所以非常快。
- **compact**：对同一个 key 只保留最后一条（`cleanup.policy=compact`）。适合"状态快照"类场景，比如 CDC 同步、配置变更流——重启后重放一遍就能重建全量状态。

所以 Kafka 的磁盘占用是**可预期的**：写入速率 × 保留时长。这也是它能扛住"亿级积压"的底气——积压对它来说只是"多留了几天的日志"。

### Q11：RabbitMQ 堆积多了为什么会出问题？

因为它的模型假设"消息很快被消费掉"。堆积意味着：

- 内存里的消息越来越多，触发**内存水位告警**，broker 开始阻塞生产者（flow control）；
- 持久化消息转写磁盘，但队列的**索引结构仍在内存**，几百万条消息的索引很吃内存；
- 经典队列的镜像模式下，每条消息要同步到所有镜像节点，堆积直接把复制压力放大。

RabbitMQ 有 **lazy queue**（尽量把消息放磁盘、内存只留索引）来缓解，但它终究不是为"存几天再处理"设计的。**判断标准很简单：你是"消息流"（Kafka）还是"任务单"（RabbitMQ）。**

## 第四层：可靠性，消息到底会不会丢？

### Q12：先问个基础问题，消息可能在哪些环节丢？

任何消息队列，链路都只有三段：**生产者 → Broker → 消费者**。丢消息只可能发生在这三段：

| 环节 | 丢失场景 | Kafka 的解法 | RabbitMQ 的解法 |
|------|----------|--------------|-----------------|
| 生产端 | 发出去但 Broker 没收到，客户端以为成功 | `acks=all` + 重试 + 幂等生产者 | publisher confirm（异步/同步） |
| Broker | 收到就宕机，数据还在内存没落盘/没同步 | 副本 + `min.insync.replicas` + ISR | 持久化（durable queue + persistent message）+ quorum queue（Raft 多数派） |
| 消费端 | 先提交位点/先 ack，再处理业务，处理挂了 | 关闭自动提交，处理完再 commit | 关闭 autoAck，处理完再 `basic.ack` |

面试答题时**一定要分三段说**，只说"Kafka 有副本不丢"会被追问到答不上来。

### Q13：Kafka 的 `acks` 三个值分别代表什么？

- `acks=0`：发出去就不管，吞吐最高，**可能丢**（网络断了也不知道）。
- `acks=1`：Leader 写入成功就返回。Leader 挂了、数据还没同步到 Follower，**会丢**。
- `acks=all`（或 `-1`）：**ISR 中所有副本都写入成功**才返回。最安全。

但 `acks=all` 有个坑：如果 ISR 只剩 Leader 自己（其他副本都掉队了），那"所有副本"就等于"1 个副本"，照样会丢。所以必须配合：

```properties
acks=all
min.insync.replicas=2          # 至少 2 个副本确认才算成功
unclean.leader.election.enable=false  # 宁可不可用，不选落后副本当 Leader
```

这三件套是"Kafka 不丢消息"的标准答案，缺一不可。代价是：副本数 3、`min.insync.replicas=2` 时，**挂掉两个副本就写不进去**——用可用性换一致性，这正是面试官想听的取舍。

### Q14：那 Kafka 数据落盘了吗？`acks=all` 就保证不丢？

不保证。`acks=all` 只保证"写进了所有 ISR 副本的**页缓存**"，**没有 fsync**。如果三台机器同时断电（机房级故障），页缓存里的数据会丢。

Kafka 的取舍是：**不做单条 fsync，靠副本冗余抗单机故障**。因为 fsync 太慢（每次几毫秒），会让吞吐断崖式下跌。真要抗机房级故障，靠的是**跨机房副本 / MirrorMaker 2 / 多集群**，而不是打开 fsync。这是一个很好的"追问反杀点"：能说出"acks=all ≠ 落盘"，说明真读过实现。

### Q15：RabbitMQ 这边怎么保证不丢？

四件事缺一不可：

1. **队列持久化**：`durable=true`（队列元数据落盘）。
2. **消息持久化**：发送时 `delivery_mode=2`（消息体落盘）。
3. **发布确认**：开启 publisher confirm，Broker 确认收到（注意：**confirm 只代表消息被 Broker 接收并路由，落盘是异步的**；要更强保证可以用 `confirm` + quorum queue）。
4. **消费手动 ack**：`autoAck=false`，业务处理成功后再 ack；处理失败 `nack(requeue=true)` 重投或进死信。

另外，经典镜像队列在 4.0 已被移除，**新版本用 quorum queue**：基于 Raft，消息写入多数派节点才算成功，天然抗单节点故障。

### Q16：为什么 Kafka 消费端"先提交位点再处理"会丢？不是有重试吗？

这是初学者最容易混的点。Kafka 的位点提交是**客户端行为**：

```java
// 错误示范：自动提交，可能"消息还没处理完，位点已经提交了"
enable.auto.commit=true
auto.commit.interval.ms=5000

// 正确姿势：处理完再手动提交
enable.auto.commit=false
poll() → 业务处理 → commitSync()/commitAsync()
```

如果自动提交在"poll 到消息"之后、"业务处理完成"之前触发，此时进程崩溃，重启后从**新位点**继续消费——中间那批消息就丢了。所以"至少一次（at-least-once）"的正确实现是：**处理成功 → 提交位点**，代价是可能重复（提交失败或提交前崩溃）。

### Q17：那重复消费怎么办？

消息队列基本只能做到 **at-least-once**（至少一次），严格 exactly-once 成本很高。工程上的标准答案是**消费端幂等**：

- 用业务唯一键（订单号 + 事件类型）做**去重表**，`INSERT ... ON DUPLICATE KEY` 或唯一索引兜底；
- 用 Redis `SETNX` 记录已处理的消息 ID（注意过期时间与业务窗口匹配）；
- 状态机校验：只允许"待支付 → 已支付"，重复的"已支付"事件直接忽略。

Kafka 另有**事务 + 幂等生产者**：`enable.idempotence=true` 解决生产端重试导致的重复（PID + 序列号去重），事务 + `isolation.level=read_committed` 解决"读-处理-写"链路的端到端 exactly-once。但它只在 Kafka 内部闭环有效，**一旦你的下游是 MySQL 或第三方接口，还是得靠业务幂等**。这也是面试高频追问。

## 第五层：消费语义——谁能消费到哪条消息？

### Q18：Kafka 的"消费组"到底是什么？为什么同一条消息有时能被多个消费者读到？

Kafka 的规则只有一句：**同一分区，同一时刻只能被同一个消费组里的一个消费者消费；不同消费组之间互不影响。**

```text
Topic: order（3 个分区）
Group A（风控）: C1 读 P0/P1，C2 读 P2       → A 组整体消费全量
Group B（积分）: C3 读 P0/P1/P2               → B 组也消费全量
```

所以"广播"在 Kafka 里是**免费的**：多开一个消费组即可，消息不用复制。而 RabbitMQ 要广播，必须**多个队列绑定同一个 fanout/topic Exchange**，每条消息在 broker 里复制 N 份——这是两种模型最直观的差异。

反过来，**RabbitMQ 的"竞争消费"**是：多个消费者订阅**同一个队列**，消息轮询派发，每条消息只被其中一个消费者拿到。想扩消费能力就加消费者，想广播就加队列。

### Q19：消费组里消费者数量超过分区数会怎样？

多出来的消费者**空转**，分不到分区。所以 Kafka 的并行度上限 = 分区数。这也是"分区数要提前规划"的原因（分区数只能增不能减，且增加会打乱 key 的路由）。

### Q20：Kafka 是推还是拉？RabbitMQ 呢？

- **RabbitMQ 是推（push）**：broker 主动把消息推给消费者，用 `basic.qos` 的 prefetch 限制"在途未确认"的消息数，防止压垮消费者。
- **Kafka 是拉（pull）**：消费者主动 `poll`，broker 端用**长轮询**（`fetch.max.wait.ms`）缓解"没数据时疯狂空转"的问题。

为什么 Kafka 选拉？因为拉模型让**消费者自己控制节奏**：处理慢就少拉点，天然背压；而且不同消费组速度不同，broker 无法同时适配所有人的推送速率。推模型延迟更低（消息一到立刻送达），拉模型更适合大批量、可回放的场景。

### Q21：顺序性怎么保证？两者差别大吗？

**Kafka**：只保证**分区内有序**。要保证同一订单的事件有序，就用订单号做 key，同一 key 必然进同一分区：

```java
producer.send(new ProducerRecord<>("order", orderId, event)); // key 决定分区
```

代价是**热点 key 会打爆单个分区**。全局有序？只能单分区，吞吐直接砍到单通道。

**RabbitMQ**：**单队列 + 单消费者**时有序。一旦多个消费者竞争同一个队列，消息被并发处理，顺序就乱了。要严格有序，要么一个队列只挂一个消费者（吞吐受限），要么按业务 key 拆多个队列（一致性哈希路由）。

另外注意：**重试会破坏顺序**。RabbitMQ 里一条消息 nack 重投会排到队尾（除非用单活跃消费者 + 本地重试）；Kafka 里处理失败如果不提交位点，会卡住整个分区（这是"分区内有序"的代价，也叫 head-of-line blocking）。

## 第六层：路由、延迟、重试、回溯——能力边界的正面交锋

### Q22：RabbitMQ 的延迟消息怎么做？Kafka 呢？

**RabbitMQ** 有三种做法：

1. **TTL + 死信队列**：消息设置过期时间，到期后进入 DLX，下游消费死信队列。坑在于**队列级 TTL 是"队头阻塞"的**——队头消息没过期，后面先过期的也出不来。要用**消息级 TTL + 每档延迟一个队列**才准。
2. **延迟插件 `rabbitmq_delayed_message_exchange`**：消息带 `x-delay` 头，Exchange 内部用定时器投递，精度好、用法简单，是生产首选。
3. 定时扫表 / 时间轮自研。

**Kafka 没有原生延迟消息**。常见方案：

- **多级延迟 Topic**：`delay-5s`、`delay-30s`、`delay-5m`，消费者到时间再转发到真实 Topic（本质是自己实现时间轮）；
- 外部调度（如时间轮服务、Redis ZSet + 定时任务）到点再投 Kafka；
- 用 Kafka 的时间戳 + 消费端过滤——**不推荐**，会堆积大量未到期消息，还会阻塞分区。

结论：**延迟/定时任务是 RabbitMQ 的主场，Kafka 要绕一大圈。**

### Q23：失败重试和死信呢？

**RabbitMQ** 是原生能力：`basic.nack(requeue=false)` 或消息过期 → 进 **DLX（死信交换机）** → 死信队列。配合 TTL 还能做"阶梯重试"（1s、5s、30s 各一个队列）。这是业务系统里非常常用的模式。

**Kafka** 没有内建重试队列，业界通用做法：

- **重试 Topic**：消费失败 → 发到 `order-retry-1`，带重试次数头，延迟消费（靠上面说的延迟方案）→ 仍失败进 `order-dlq`；
- **阻塞重试（Spring Kafka 的 `@RetryableTopic`）**：自动创建重试/死信 Topic，本质还是上面的方案；
- 简单粗暴：本地重试 N 次，仍失败就记录到 DB 人工处理。

这也是选型时容易被忽略的一点：**Kafka 把"业务语义"留给了应用层**，它只保证"日志可靠、可回放"；RabbitMQ 把"路由、重试、死信、优先级"做进了协议。

### Q24：什么叫"消息回溯"？为什么这个能力很重要？

Kafka 的 offset 是客户端自己记的，所以可以 `seek` 到任意位置重读：

```bash
# 把某个消费组的位点重置到 24 小时前
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group order-service --reset-offsets --to-datetime 2026-11-25T00:00:00.000 \
  --topic order --execute
```

典型用途：

- 新上线一个下游服务，**从头回放历史数据**做初始化；
- 消费逻辑有 bug，修完**重放**受影响时间段的数据；
- 实时链路和离线链路读同一份数据（Lambda 架构）。

RabbitMQ 消费即删，**没有回溯概念**。要"重放"，只能在生产端重新发一遍，或依赖业务侧落库。这一条直接决定了：**需要"以数据流为中心"的场景（CDC、事件溯源、流计算、审计），只能选 Kafka。**

### Q25：那 Kafka 的"消息保留"会不会导致消费不到旧数据？

会。默认只留 7 天，超过就删。如果下游停了 8 天，回来发现位点越界（`OffsetOutOfRange`），只能按 `auto.offset.reset` 选 `earliest`（从现存最早）或 `latest`（从最新）——**中间的数据永久丢失**。所以 Kafka 上的"消费方"要有监控：**消费延迟（lag）必须告警**，不能等积压 7 天才发现。

补充一句：新版 Kafka 有 **Tiered Storage（分层存储）**，把旧 segment 卸到对象存储，保留期可以拉长到月/年，成本大幅下降。这是"Kafka 也要做长期存储"的信号。

## 第七层：集群与扩展，谁更容易长大？

### Q26：RabbitMQ 集群为什么扩展性一般？

理解三点：

1. **元数据全量复制**：集群所有节点的 Erlang/Mnesia 都存全量元数据（队列、交换机、绑定关系），节点越多，同步成本越高（新版用 Khepri 改进了这一点，但本质仍是全量元数据）。
2. **队列是单点**：一个队列（经典队列）只存在于一个节点上，其他节点只是"知道它在哪"。所以**队列的吞吐不会因为加节点而变高**，只能把不同队列分散到不同节点。
3. **镜像复制代价高**：经典镜像队列把每条消息同步到所有镜像，节点越多写越慢。**Quorum Queue 用 Raft 三/五副本**，好一些，但仍是"每个队列一组 Raft"，队列数量多时开销明显。

所以 RabbitMQ 的扩展方式是**垂直 + 多队列分散**，不是"加机器就线性变快"。

### Q27：Kafka 为什么能水平扩展？

因为**分区是天然的并行单元**：

- Topic 的 3 个分区可以分布在 3 台 Broker 上，**读写压力天然分摊**；
- 加 Broker 后做分区迁移（`kafka-reassign-partitions`），把部分分区搬过去；
- 生产者和消费者都按分区并行，**没有中心化的"队列状态"瓶颈**（Controller 只管元数据，不在数据路径上）。

代价是**运维复杂度**：分区规划、副本分布、磁盘容量、Controller 故障、rebalance 抖动，都要人来管。所以有句话：**Kafka 的扩展性是"用运维复杂度换来的"。**

### Q28：分区数是不是越多越好？

不是。分区数增加会带来：

| 成本 | 说明 |
|------|------|
| 文件句柄 | 每个分区每个 segment 都占 fd，分区多了直接打满 `ulimit` |
| 端到端延迟 | 攒批更难凑满、故障恢复要并行拉更多分区 |
| 故障恢复时间 | Leader 切换要恢复更多分区的状态 |
| Controller/元数据压力 | 分区数上万时，Controller 的元数据同步和选举明显变慢 |
| 不可逆 | **Kafka 不支持减少分区**；增加分区会破坏 key 到分区的映射，同 key 消息可能落到不同分区，顺序性被破坏 |

经验值：**分区数 ≈ 目标吞吐 / 单分区吞吐**，再留 1.5~2 倍余量给未来扩容和消费组并行；一般单 Topic 十几个到几十个分区足够，除非是超大流量。

### Q29：Rebalance 是什么？为什么会"抖"？

消费组成员变化（上线、下线、崩溃、订阅变更）会触发 **Rebalance（再平衡）**：重新分配"分区 → 消费者"的归属。

老版本（eager 协议）是**全停**：所有消费者放弃全部分区，重新加入组、重新分配，期间**整个消费组暂停消费**。消费组大、分区多时，一次 rebalance 能停几十秒，消息积压瞬间飙升。

优化手段（面试加分项）：

- **Cooperative Sticky（增量再平衡）**：只迁移需要变动的分区，其他消费者继续消费；
- **static membership（`group.instance.id`）**：滚动重启/短暂掉线不触发 rebalance；
- **调大 `session.timeout.ms` / `max.poll.interval.ms`**：减少误判（但注意 `max.poll.interval.ms` 太小会把"处理慢"误判为死亡）；
- **KIP-848 新协议**（Kafka 4.0 默认）：把分配逻辑从客户端移到 broker，大幅降低 rebalance 停顿。

### Q30：Kafka 的 ZooKeeper 是干嘛的？现在还要吗？

老架构里 ZK 存元数据（Broker 注册、Topic 配置、Controller 选举、ACL），Controller 靠 ZK watch 感知变化。问题是：**元数据规模大时 ZK 成为瓶颈，Controller 故障恢复慢，还要多维护一套系统**。

**KRaft 模式**（KIP-500）用 Kafka 自己实现的 Raft 管理元数据，**Kafka 4.0 已完全移除 ZooKeeper**。收益：部署更简单、Controller 切换秒级、支持更多分区（百万级）。面试如果问"Kafka 为什么去 ZK"，答"元数据瓶颈 + 运维简化 + 选举性能"即可。

## 第八层：那到底怎么选？

### Q31：有没有一张表能直接对完？

| 维度 | Kafka | RabbitMQ |
|------|-------|----------|
| 核心抽象 | 分区日志（append-only） | Exchange + Queue（任务派发） |
| 消息消费后 | 保留（按时间/大小/compact） | 删除 |
| 消费模式 | 拉（长轮询），按 offset | 推，按 prefetch 流控 |
| 广播 | 多消费组天然支持 | 多队列绑定 Exchange（消息复制） |
| 路由能力 | 弱（只有 topic/partition） | 强（direct/fanout/topic/headers） |
| 顺序性 | 分区内有序 | 单队列单消费者有序 |
| 吞吐 | 极高（单分区数十万，集群百万+） | 中高（单队列数万，集群十万级） |
| 延迟 | 毫秒~几十毫秒（受攒批影响） | 亚毫秒~毫秒 |
| 堆积能力 | 极强（为积压设计） | 一般（需 lazy queue / 限流） |
| 回溯重放 | 原生支持（seek offset） | 不支持 |
| 延迟消息 | 无原生支持，需自建 | 原生（TTL+DLX / 延迟插件） |
| 重试/死信 | 需自建重试 Topic | 原生 DLX / TTL |
| 消息优先级 | 不支持 | 支持（priority queue） |
| 事务/Exactly-once | 幂等生产者 + 事务（闭环内） | 无端到端 EOS，靠 confirm + ack + 幂等 |
| 集群扩展 | 分区水平扩展，线性 | 队列分散，扩展有限 |
| 运维成本 | 高（分区/副本/磁盘规划） | 中（管理界面友好） |
| 典型场景 | 日志、埋点、CDC、流计算、事件溯源、削峰 | 业务解耦、任务分发、复杂路由、RPC、低延迟通知 |

### Q32：能不能给一条决策路径？

```text
需要回放历史 / 多下游各自全量消费 / 海量日志埋点 / 流式计算？
  ├─ 是 → Kafka
  └─ 否 ↓
需要复杂路由（按规则分发到多个业务方）/ 延迟消息 / 优先级 / 单条重试死信？
  ├─ 是 → RabbitMQ
  └─ 否 ↓
消息量级？
  ├─ 峰值 > 10 万/秒，或需要扛长时间积压 → Kafka
  ├─ 万级/秒，要求低延迟、强业务语义 → RabbitMQ
  └─ 都很小 → 甚至可以先用 Redis Stream / 数据库任务表，别上重武器
```

补充两条现实因素：

- **团队能力**：Kafka 运维门槛明显更高（分区规划、磁盘、监控 lag、rebalance 调优）。小团队上 Kafka 常常"用得起、养不起"。
- **两个都上很正常**：大厂典型架构是 **Kafka 做数据管道 + RabbitMQ 做业务消息**。比如埋点走 Kafka 进数仓，订单状态变更走 RabbitMQ 通知各业务方。它们不是替代关系，而是"日志"和"消息路由"两种不同工具的并存。

### Q33：有没有"看起来像 A，其实该用 B"的坑？

几个真实反例：

- **拿 RabbitMQ 收全站日志**：日志量大、要回放、要多下游，RabbitMQ 会堆积到内存告警、磁盘打满，还无法重放。→ 该用 Kafka。
- **拿 Kafka 做订单超时关闭**：需要"30 分钟没支付就关单"，Kafka 没有延迟消息，只能自己搭时间轮 + 延迟 Topic，复杂度高还容易积压。→ 该用 RabbitMQ 延迟插件，或直接用 Redis ZSet / 定时任务。
- **拿 Kafka 做 RPC**：Kafka 没有请求-响应语义，自己拼 correlationId + 回复 Topic，延迟还高。→ 用 RabbitMQ 的 `reply_to`，或直接 gRPC。
- **拿 RabbitMQ 做"新服务上线回放历史"**：消息早删了，回放不了。→ Kafka。

## 快问快答（面试前的 10 分钟）

**Q：一句话说清两者区别？**
A：RabbitMQ 是"消息路由器"，消息被消费即删除，强在路由、低延迟、业务语义；Kafka 是"分布式提交日志"，消息按保留策略存储、可回放，强在吞吐、堆积、多下游消费。

**Q：Kafka 为什么快？**
A：顺序写 + 页缓存 + 零拷贝 + 批量（生产/存储/消费三段）+ 分区并行 + 消费端无 broker 状态。

**Q：Kafka 会丢消息吗？**
A：会。三段分别防：生产端 `acks=all` + 重试 + 幂等；Broker 端副本 + `min.insync.replicas≥2` + `unclean.leader.election=false`；消费端关闭自动提交、处理完再 commit。注意 `acks=all` 不等于 fsync 落盘。

**Q：RabbitMQ 会丢消息吗？**
A：会。队列 durable + 消息 persistent + publisher confirm + 手动 ack，四件套；新版用 quorum queue（Raft）替代镜像队列。

**Q：怎么保证不重复消费？**
A：做不到严格不重复（at-least-once），只能消费端幂等：唯一键去重表 / Redis SETNX / 状态机。Kafka 可用幂等生产者 + 事务解决内部重复。

**Q：怎么保证顺序？**
A：Kafka 用 key 路由同一分区（分区内有序，热点 key 是代价）；RabbitMQ 单队列单消费者（吞吐是代价）。注意重试和 rebalance 都会破坏顺序。

**Q：Kafka 为什么是拉模型？**
A：消费者自控节奏、天然背压、适配不同速度的消费组；长轮询避免空转。

**Q：分区数怎么定？**
A：目标吞吐 / 单分区吞吐，留 1.5~2 倍余量；考虑 fd、rebalance 成本、不可减少、key 路由稳定性。

**Q：RabbitMQ 怎么实现广播？**
A：多个队列绑定同一个 fanout/topic Exchange，每条消息在 broker 复制 N 份。Kafka 则是多开消费组，消息不复制。

**Q：积压百万条怎么办？**
A：先看是"消费慢"还是"生产暴涨"。扩消费者（不超过分区数）/ 扩分区（注意 key 乱序）/ 提升单条处理效率（批量、异步、减少 DB 往返）/ 临时降级（先落库后处理）。RabbitMQ 还要防内存告警阻塞生产。

## 面试背诵卡

### 1. 定位（先说这一句，定基调）

> **RabbitMQ = 消息路由器**（AMQP，Exchange 路由，消费即删，低延迟业务消息）；
> **Kafka = 分布式提交日志**（分区 append-only，offset 消费，可回放，高吞吐数据管道）。

### 2. 五个必须能展开的差异

| # | 差异 | 一句话展开 |
|---|------|-----------|
| 1 | 数据模型 | 队列 vs 分区日志 → 决定"消费即删" vs "可回放" |
| 2 | 消费模型 | push + prefetch vs pull + offset |
| 3 | 路由能力 | 四种 Exchange vs 仅 topic/partition |
| 4 | 吞吐与延迟 | 顺序写/零拷贝/批量 vs 单条状态管理 |
| 5 | 生态能力 | DLX/TTL/优先级/延迟插件 vs 流处理/CDC/分层存储 |

### 3. 必背参数

**Kafka**

```properties
# 可靠性
acks=all
min.insync.replicas=2
enable.idempotence=true
unclean.leader.election.enable=false

# 消费语义
enable.auto.commit=false
isolation.level=read_committed

# 吞吐调优
linger.ms=5~50
batch.size=16KB~1MB
compression.type=lz4/zstd
fetch.min.bytes=1
max.poll.records=500
```

**RabbitMQ**

```text
durable=true + delivery_mode=2      # 持久化
publisher confirm                   # 生产确认
basic.qos(prefetch=N)               # 流控
autoAck=false + 手动 ack/nack       # 消费确认
x-dead-letter-exchange / x-message-ttl  # 死信/延迟
quorum queue                        # Raft 高可用（替代镜像队列）
lazy queue                          # 抗堆积
```

### 4. 答题模板（被问"如何选型"时）

> **结论**：默认按"数据流 vs 业务消息"分流。
> **依据**：吞吐/堆积/回放选 Kafka；路由/延迟/低延迟/重试选 RabbitMQ。
> **取舍**：Kafka 用运维复杂度换扩展性，RabbitMQ 用吞吐上限换业务语义。
> **落地**：我们项目是 X 场景，所以我选 Y，理由是 Z（举一个 lag 监控、分区数、DLX 的具体细节）。

### 5. 高频追问链（提前准备到第三层）

```text
Q: Kafka 为什么快？
 → 顺序写 + 零拷贝 + 批量 + 页缓存
Q: 零拷贝具体省了什么？
 → 用户态拷贝 2 次 + 上下文切换 2 次，sendfile 直达网卡
Q: 那为什么不用 mmap 写？
 → 写用 append + page cache，读用 sendfile；mmap 适合读不适合持续追加（页回收/缺页成本）

Q: Kafka 怎么保证不丢？
 → acks=all + ISR + min.insync.replicas
Q: ISR 缩到 1 怎么办？
 → 写失败（min.insync 不满足），或容忍丢数据（unclean election），二者取舍
Q: HW 和 LEO 区别？
 → LEO 是副本末尾，HW 是 ISR 最小 LEO，消费者只能读到 HW 之前

Q: 消费组 rebalance 怎么优化？
 → cooperative sticky + static membership + 调参 + KIP-848
Q: rebalance 期间消息会丢吗？
 → 不会丢，只是暂停消费、lag 上涨；重复消费才需要幂等

Q: RabbitMQ 集群为什么扩展性差？
 → 元数据全量复制 + 队列单点 + 镜像同步成本
Q: quorum queue 和镜像队列区别？
 → Raft 多数派 vs 全量镜像；后者 4.0 已移除
```

### 6. 最容易答错的五个点

1. 说"Kafka 写磁盘所以慢"——错，顺序写 + 页缓存，比随机写快得多。
2. 说"`acks=all` 就绝对不丢"——错，没 fsync，且 ISR 可能缩水。
3. 说"Kafka 一条消息只能被一个消费者消费"——错，是"同一消费组内"。
4. 说"RabbitMQ 加机器就能线性扩容"——错，队列是单点，只能分散。
5. 说"Kafka 能做延迟消息"——原生不支持，要自建。
