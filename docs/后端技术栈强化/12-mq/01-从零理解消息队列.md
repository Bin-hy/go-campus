# 从零理解消息队列：它到底解决什么问题

> 专题第 1 篇 · 下一篇：[Kafka 架构全景](./02-Kafka-架构全景)
> 这一篇不碰任何参数，只回答三个问题：为什么需要 MQ、它长什么样、什么时候**不该**用。

## 一、从一次下单请求说起

假设下单接口要做四件事：扣库存、发短信、加积分、写审计日志。

```text
用户请求 → 订单服务 → 扣库存 50ms → 发短信 200ms → 加积分 30ms → 写日志 20ms → 返回
```

**Q：这样写有什么问题？看起来能跑通。**

三个问题，每个都能在生产上出事故：

1. **慢**：用户等了 300ms，其中 200ms 花在「发短信」上——可短信成功与否不影响下单成功。
2. **脆**：短信服务超时，整条下单链路失败。用户会问：短信发不出去，为什么我的订单下不了？
3. **扛不住峰值**：秒杀时每秒 1 万个请求打进来，扣库存服务被打穿，数据库连接池耗尽，全线雪崩。

再看加一层消息队列之后：

```text
用户请求 → 订单服务 → 写一条"OrderCreated"消息（5ms）→ 返回
                         ↓
              短信服务 / 积分服务 / 审计服务各自消费
```

**Q：这不就是把问题藏起来了吗？短信服务该慢还是慢啊。**

对，短信服务该慢还是慢，但**慢的代价被隔离了**：

- 用户不再等它（异步）；
- 它挂了，消息留在队列里，恢复后继续消费（解耦）；
- 峰值时消息先堆着，下游按自己的速度消费（削峰）。

所以 MQ 的本质不是「传消息」，而是**把「必须现在、必须一起做」拆成「可以稍后、各自做」**。它买的不是速度，是**时间和依赖上的解耦**。

## 二、三个经典价值，和它们各自的代价

| 价值 | 典型场景 | 代价 / 副作用 |
|------|----------|---------------|
| **异步** | 注册后发券、下单后发短信 | 用户看到的结果是「最终一致」；失败要补偿、要可观测 |
| **解耦** | 订单事件广播给积分、风控、推荐 | 链路变长，问题定位变难；消息格式成了跨团队契约 |
| **削峰** | 秒杀、大促、批量导入 | 下游必须能接受「延迟消费」；积压要有监控和告警 |

**Q：那是不是所有调用都该走 MQ？**

不是，而且这是面试里很常见的反问。不该用的信号：

- **需要同步结果**：查询余额、校验库存够不够，必须当场拿到答案；
- **强一致、不能最终一致**：转账扣款，不能「稍后再说」；
- **调用量很小且稳定**：加 MQ 只是给自己增加一套要运维的中间件；
- **团队没有运维能力**：Kafka 养不好，lag 和磁盘能把人拖垮。

一句话：**MQ 是在「一致性」和「复杂度」上借债，换「吞吐」和「解耦」。** 借之前先确认自己还得起。

## 三、两种世界观：任务队列 vs 提交日志

这是理解 Kafka 和 RabbitMQ 差异的**总开关**。

### 世界观 A：消息是「待办任务」，处理完就该消失

RabbitMQ 是这种世界观。生产者把消息交给交换机，交换机路由到队列，消费者取走并确认（ack），**消息随后被删除**。

生活比喻：**快递驿站**。包裹送到驿站，分拣上架，你取走一个，货架就空一格。你没取，它就一直在那儿占地方。

由此推出 RabbitMQ 的性格：

- 关心「这条消息该派给谁」（路由能力）；
- 关心「消费者处理完了吗」（ack、重投、死信）；
- 关心「别把消费者压垮」（prefetch 流控）；
- 不擅长「留着以后再看」（堆积能力有限，不能回放）。

### 世界观 B：消息是「已发生的事实」，记下来就不该改

Kafka 是这种世界观。消息按顺序追加到分区日志里，**消费只是移动一个叫 offset 的读数位置，不影响消息本身**。消息按时间或大小过期后才删除。

生活比喻：**报纸合订本 / 电视节目**。节目照常播出，谁看谁不看，电视台不关心；每个观众自己记「我看到第几页」。想看上周的？带子还在就能回看。

由此推出 Kafka 的性格：

- 吞吐优先：顺序追加、批量、零拷贝；
- 多下游友好：每个消费组各自记 offset，一份数据服务多方；
- 可回放：算错了能重跑，新服务能补历史；
- 路由能力弱：只有 Topic / Partition，没有 Exchange 那套规则；
- 业务语义留给应用层：重试、死信、延迟都得自己搭。

**Q：为什么会有这两种世界观？是设计者随便选的吗？**

不是，是**出生场景**决定的：

- RabbitMQ（2007，AMQP）出生在**企业应用集成**：ERP、CRM、订单系统之间要可靠地派发任务，路由和确认是刚需。
- Kafka（2011，LinkedIn）出生在**日志聚合**：几千台机器的日志要汇到一起，喂给实时计算和离线数仓。数据量巨大、要多方重复读、要能重跑——「日志 + offset」是最自然的模型。

所以「Kafka 比 RabbitMQ 先进」是个错误命题。**它们是两种不同工具，被用错了地方才显得谁不行。**

## 四、选型前必须问清的五个问题

不要一上来就比吞吐。先回答这五个问题，答案基本就决定了选谁：

| # | 问题 | 偏向 Kafka | 偏向 RabbitMQ |
|---|------|-----------|---------------|
| 1 | 消息被消费后还需要吗？ | 需要回放/多下游读全量 | 处理完即结束 |
| 2 | 需要按复杂规则分发吗？ | 不需要，按主题分流即可 | 需要按 routing key / header 精确路由 |
| 3 | 有延迟消息、优先级、单条重试吗？ | 少见，可自建 | 常见，且希望开箱即用 |
| 4 | 峰值和积压有多大？ | 十万级/秒以上，或要扛几天积压 | 万级/秒，要求低延迟 |
| 5 | 团队能养得起吗？ | 有专人管分区、磁盘、lag | 希望运维简单、界面友好 |

**Q：五个问题里有冲突怎么办？**

按「数据模型」优先，而不是按性能优先。比如「需要回放」这一条只要成立，就该选 Kafka——RabbitMQ 再快也给不了回放。反过来，如果只是下单后发个通知、失败了重试三次进死信，Kafka 要你手搓一堆东西，RabbitMQ 一个 DLX 就解决了。

## 五、术语对照：先混个脸熟

后面两篇会逐个展开，这里先建立映射，避免读串：

| 你想表达 | Kafka 里叫什么 | RabbitMQ 里叫什么 |
|----------|----------------|-------------------|
| 消息分类 | Topic | Exchange（交换机）+ Queue |
| 分片/并行单位 | Partition（分区） | Queue（队列，本身是单点） |
| 副本 | Replica（Leader/Follower） | quorum queue 的 Raft 副本 /（旧）镜像队列 |
| 消费进度 | offset | ack（未确认消息集合） |
| 广播给多个下游 | 多个消费组 | 多个队列绑定同一 Exchange |
| 消费失败重试 | 自建重试 Topic | nack + requeue / DLX |
| 消息积压 | 正常现象，受保留期约束 | 需要流控、lazy queue 缓解 |
| 消息删除 | 按保留策略过期 | 消费 ack 后删除 |
