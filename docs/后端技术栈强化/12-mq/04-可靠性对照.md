# 可靠性对照：消息到底在哪一段丢

> 专题第 4 篇 · 上一篇：[RabbitMQ 架构全景](./03-RabbitMQ-架构全景) · 下一篇：[消费语义与顺序](./05-消费语义与顺序)
> 目标：把「不丢消息」拆成可验证的三段，给出两者的配置组合与各自的失效边界。

## 一、先分段：丢消息只有三种可能

任何 MQ 的链路都是三段：**生产者 → Broker → 消费者**。对应三种丢失方式：

| 段 | 丢失方式 | Kafka 的防线 | RabbitMQ 的防线 |
|----|----------|--------------|-----------------|
| 生产 | 网络抖动/超时，客户端以为成功 | `acks=all` + 重试 + 幂等生产者 | publisher confirm + 重发 |
| Broker | 收到后宕机，数据在内存/单副本 | 多副本 + `min.insync.replicas` + 禁止 unclean 选主 | durable + persistent + quorum queue（Raft 多数派） |
| 消费 | 先提交位点/先 ack 再处理业务 | 关闭自动提交、处理完再 commit | 关闭 autoAck、处理完再 ack |

**Q：为什么一定要分段？直接说「Kafka 有副本不丢」不行吗？**

因为面试官下一句一定是「副本还没同步完 Leader 就挂了怎么办」「生产者以为失败其实写成功了怎么办」「消费者提交了位点但业务回滚了怎么办」。**分三段是唯一能覆盖全部追问的框架**。

## 二、生产端：怎么确认「真的发出去了」

### 2.1 Kafka：acks 与重试

```properties
acks=all                 # 等 ISR 全部写入
retries=2147483647       # 默认无限重试（受 delivery.timeout.ms 限制）
delivery.timeout.ms=120000
enable.idempotence=true  # 幂等生产者：去重 + 保序
max.in.flight.requests.per.connection=5   # 开幂等后可 >1
```

三个必须理解的细节：

1. **`acks=all` 等的是 ISR，不是全部副本**。ISR 缩到 1 时，它等价于 `acks=1`。所以必须配 `min.insync.replicas`。
2. **重试会带来重复**。生产者没收到 ack 就重发，Broker 可能已经写成功了——所以生产端要幂等（`enable.idempotence=true`），它用 `PID + 序列号` 在 Broker 端去重。
3. **重试会带来乱序**（未开幂等时）。第一批失败重试，第二批先成功，顺序就反了。开幂等后 Kafka 会保证单分区内的顺序。

配置组合的标准答案：

```properties
# Broker 端
default.replication.factor=3
min.insync.replicas=2
unclean.leader.election.enable=false
```

含义：3 副本里至少 2 个同步才算写入成功；宁可分区不可写，也不让落后副本当 Leader（否则丢已确认数据）。

**Q：这样配置的代价是什么？**

可用性下降。3 副本挂 2 个，该分区就**拒绝写入**（`NOT_ENOUGH_REPLICAS`）。这是用「写不可用」换「不丢数据」，面试要主动说出这个 trade-off。

### 2.2 RabbitMQ：publisher confirm

```go
ch.Confirm(false)                       // 开启 confirm 模式
confirms := ch.NotifyPublish(make(chan amqp.Confirmation, 100))

err := ch.PublishWithContext(ctx, "", "order.create", false, false,
    amqp.Publishing{
        DeliveryMode: amqp.Persistent,   // 消息持久化
        ContentType:  "application/json",
        Body:         body,
    })

select {
case c := <-confirms:
    if !c.Ack { /* Broker 拒收，需重发或告警 */ }
case <-time.After(5 * time.Second):
    /* 超时：结果未知，重发前必须做幂等 */
}
```

关键语义：

- confirm 的 ack 表示**Broker 已接收并完成入队**；
- 对 classic 队列的持久化消息，**confirm 不等于 fsync**，机器掉电仍可能丢；
- 对 **quorum 队列**，消息写入多数派 Raft 日志后才 confirm，可靠性接近 Kafka 的 `acks=all`；
- confirm 是异步的，生产上要攒批确认（`multiple`）而不是每条同步等。

**Q：为什么不用 AMQP 事务（tx.select）？**

事务是同步的、每条消息都要等提交，吞吐会掉一个数量级。publisher confirm 是异步批量确认，效果足够且快得多，所以生产上几乎只用 confirm。

## 三、Broker 端：写进去了就安全吗

### 3.1 Kafka：副本 + HW + 刷盘

| 故障 | 会不会丢 | 说明 |
|------|----------|------|
| 单 Broker 宕机 | 不丢（配 3 副本） | Leader 从 ISR 重选，HW 之前的消息一定在 |
| 单盘损坏 | 不丢（副本在其他盘） | 副本目录分散在不同 Broker |
| 机房断电（全宕） | **可能丢** | 只写页缓存未 fsync，三台同时断电会丢最后一段 |
| ISR 缩到 1 时宕机 | **可能丢** | 没有其他同步副本，`min.insync.replicas` 会阻止继续写 |
| 落后副本被选为 Leader | **会丢** | `unclean.leader.election.enable=true` 时才会发生 |

**Q：为什么 Kafka 不每条 fsync？**

fsync 是毫秒级操作，每条都刷会让吞吐掉到几千 TPS。Kafka 的选择是：**用副本冗余对抗单机故障，用跨机房复制对抗机房故障**，而不是把可靠性压在单机磁盘上。要更强保证就上 `acks=all` + 3 副本 + 跨 AZ 部署。

### 3.2 RabbitMQ：持久化与 quorum

四件套缺一不可：

```text
队列 durable=true  +  消息 delivery_mode=2  +  publisher confirm  +  quorum queue（或可靠的存储）
```

- classic 队列的持久化消息：**不是每条 fsync**，Broker 崩溃可能丢最后一批；
- quorum 队列：Raft 日志，多数派落盘才确认，容忍少数节点故障；
- 注意：**非持久化消息进了 quorum 队列也会被复制**（quorum 队列不支持非持久化语义）。

**Q：既然 quorum 更可靠，为什么不全用 quorum？**

成本：每个队列一个 Raft 组，写入要多数派确认，吞吐低于 classic；队列数量多时 Raft 组的管理开销明显。所以常见做法是：**关键业务队列用 quorum，临时/可重建的队列用 classic**。

## 四、消费端：三种提交时机，三种语义

这是丢消息和重复消费的**主战场**。

| 时机 | 语义 | 后果 |
|------|------|------|
| 先提交/ack，后处理 | at-most-once | 处理失败或崩溃 → **消息永久丢失** |
| 先处理，后提交/ack | at-least-once | 崩溃在提交前 → **重复消费** |
| 处理与提交原子化 | exactly-once | 成本高，通常只在 Kafka 内部闭环可行 |

### 4.1 Kafka 的位点提交

```java
// 错误：自动提交可能在处理完成前发生
enable.auto.commit=true
auto.commit.interval.ms=5000

// 正确：处理成功后手动提交
enable.auto.commit=false
while (true) {
    records = consumer.poll(Duration.ofMillis(500));
    process(records);                 // 业务处理
    consumer.commitSync();            // 处理完再提交
}
```

`commitSync` 失败会阻塞重试，`commitAsync` 不重试但可能丢失最后一次提交（通常配合周期性同步提交兜底）。

**Q：poll 到一批消息，处理到第 3 条时进程被 kill，会怎样？**

取决于提交粒度：整批提交 → 整批重放；逐条提交 → 重放第 3 条之后。无论哪种，第 3 条都可能被处理两次（如果它在提交前已经产生副作用）。所以**重复不可避免，幂等必须做**。

### 4.2 RabbitMQ 的 ack

```go
msgs, _ := ch.Consume("order.create", "", false, false, false, false, nil) // autoAck=false
for d := range msgs {
    if err := handle(d.Body); err != nil {
        d.Nack(false, true)   // requeue=true：重回队列（可能死循环！）
        continue
    }
    d.Ack(false)
}
```

两个坑：

1. **`autoAck=true`**：投递即确认，消费者崩溃消息就没了；
2. **`Nack(requeue=true)` 死循环**：一条毒消息会无限重投，打满 CPU。正确做法是**限制重试次数**（用 `x-death` 头计数），超过就 `requeue=false` 进死信队列。

## 五、Exactly-Once：能到哪一步

### 5.1 Kafka 的事务闭环

```properties
enable.idempotence=true
transactional.id=order-tx-01
isolation.level=read_committed   # 消费者只读已提交事务
```

能力边界：

- **生产端**：幂等 + 事务，保证「重试不重复」「一批写入原子可见」；
- **消费-处理-生产**：`sendOffsetsToTransaction` 把「写结果 + 提交位点」放进同一事务，实现 Kafka 内部的读-处理-写闭环；
- **一旦跨出 Kafka**（写 MySQL、调第三方），事务失效，**必须靠业务幂等**。

**Q：为什么写数据库就不能 exactly-once？**

因为数据库事务和 Kafka 事务是两个系统，没有分布式事务协议把它们绑在一起（两阶段提交能绑，但代价大、可用性差）。工程上的通用解法是**本地消息表 / 事务消息 / 幂等消费**，本质都是「最终一致 + 去重」。

### 5.2 RabbitMQ 没有 EOS

RabbitMQ 只提供 at-least-once 的工具（confirm + 手动 ack + 持久化），**没有事务性消费**。所谓「RabbitMQ 事务」只是 AMQP 的发布事务，不覆盖消费侧。所以：

- 生产端：confirm + 重发（幂等）；
- 消费端：手动 ack + 幂等处理；
- 不要承诺「MQ 层保证不重复」。

### 5.3 幂等的三种落地方式

| 方式 | 做法 | 适用 |
|------|------|------|
| 唯一键去重 | 消息 ID / 业务键建唯一索引，重复插入失败即忽略 | 写库场景，最可靠 |
| 状态机 | 只允许 `待支付 → 已支付`，重复事件直接跳过 | 状态流转类业务 |
| 分布式去重表 | Redis `SETNX` + 过期时间 | 高并发、可容忍少量误判 |

```sql
-- 去重表：同一订单同一事件只能落一次
INSERT INTO consumed_event(event_id, order_id, created_at)
VALUES (?, ?, NOW())
ON DUPLICATE KEY UPDATE event_id = event_id;  -- 影响行数 0 表示重复
```

## 六、一张总表：配置到位了吗

| 检查项 | Kafka | RabbitMQ |
|--------|-------|----------|
| 生产确认 | `acks=all` | publisher confirm |
| 副本/持久化 | RF=3 | durable + persistent（或 quorum） |
| 最小同步数 | `min.insync.replicas=2` | quorum 多数派 |
| 禁止落后选主 | `unclean.leader.election=false` | —（Raft 天然多数派） |
| 消费确认 | 手动 commit | 手动 ack |
| 重试上限 | `delivery.timeout.ms` + 重试 Topic | `x-death` 计数 + DLX |
| 幂等 | 幂等生产者 / 业务幂等 | 业务幂等 |
| 监控 | consumer lag、ISR 变化、UnderReplicated | ready/unacked、队列深度、blocked 连接 |
