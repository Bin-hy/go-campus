# 消息怎么不丢、不重？—— 生产消费语义

> 属于 S3 Kafka 深入 · 第二篇
> 上一篇：[架构与存储](./架构与存储)　下一篇：[可靠性与积压](./可靠性与积压)

用消息队列，最头疼的两件事是"消息丢了"和"消息重复了"。这背后是生产者和消费者两端的语义设计。这一篇把它们讲透。

## 生产者：重试带来的重复，用幂等解决

生产者发消息失败会重试，但网络超时有个尴尬：**消息可能已经写进去了，只是确认没回来**，重试就导致同一条消息被写两次。幂等生产者解决的就是"重复发送导致的重复"。

实现很简单：给每个生产者分配一个 **PID（Producer ID）+ 每个分区一个单调递增的序列号（sequence）**。Broker 记录每个分区已收到的最大序号，收到序号 ≤ 已收到的，就**丢弃**。注意幂等的边界：它只保证"单分区、单会话内"不重复，生产者重启 PID 就变了。

跨分区的原子写入，要用**事务**：开启事务、写多个分区、一起提交或中止。事务 + 幂等 + 消费者的"读已提交"，才能做到端到端 exactly-once。

## 消费者：消费组和 offset

多个消费者组成一个**消费组（Consumer Group）**，组内**一个分区只能被一个消费者消费**。所以消费者实例数超过分区数时，多出的实例会空闲——这就是"分区数是并行度上限"的由来。

消费者的进度用 **offset** 记录。这里有个关键选择：

- **自动提交**：定时自动提交 offset，省事，但可能"处理前崩溃导致丢消息"或"处理后崩溃导致重复"。
- **手动提交**：业务处理完再提交，配合"先处理后提交"实现 **at-least-once**（至少一次，可能重复，但不会丢）。

三种投递语义：at-most-once（最多一次，可能丢）、**at-least-once（至少一次，可能重复，默认推荐）**、exactly-once（恰好一次）。工程上普遍用 **at-least-once + 消费者幂等**，用幂等把重复消化掉。

## rebalance：消费组的"地震"

当组内成员变化（实例加入/退出/宕机）或分区数变化时，会触发 **rebalance**——重新把分区分配给消费者。

rebalance 最大的危害是**期间组内所有消费者停止消费**（STW），频繁 rebalance 会导致吞吐骤降、消息积压。触发原因常见三种：实例加入/退出、订阅的分区数变化、消费者处理消息过久超过 `max.poll.interval.ms` 被踢出。

减少 rebalance 的办法：调大 `max.poll.interval.ms` 和 `session.timeout.ms`（避免误判）、保持实例数量稳定、用**静态成员**（`group.instance.id`）避免重启触发 rebalance。

## 串起来

消息"不丢不重"是两端配合的结果：生产者靠 acks + 重试 + 幂等 + 事务，消费者靠手动提交 + 幂等；而 rebalance 是消费组动态调整的代价，要理解它的触发条件和规避手段。下一篇文章把这些串成完整的可靠性方案，并处理"消息积压"这个线上常见故障。
