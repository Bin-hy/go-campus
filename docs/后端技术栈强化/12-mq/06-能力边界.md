# 能力边界：路由、延迟、重试、回溯、堆积

> 专题第 6 篇 · 上一篇：[消费语义与顺序](./05-消费语义与顺序) · 下一篇：[选型与面试](./07-选型与面试)
> 目标：把「谁能原生做到、谁要自己搭、搭出来有什么坑」讲清楚，避免选型时想当然。

## 一、路由：精细分发 vs 主题分流

| 能力 | RabbitMQ | Kafka |
|------|----------|-------|
| 按 key 精确匹配 | direct exchange | 只能靠 Topic 名约定 |
| 广播 | fanout exchange | 多消费组（不复制消息） |
| 通配符 | topic exchange（`*`、`#`） | 无 |
| 按属性路由 | headers exchange | 无（应用层过滤） |
| 路由失败通知 | mandatory + basic.return / alternate exchange | 无「路由」概念 |

**Q：Kafka 想按事件类型分发给不同团队，怎么办？**

三种做法，复杂度递增：

1. **一个 Topic 多消费组**：各团队都订阅全量，自己过滤。简单，但浪费带宽与消费能力；
2. **拆多个 Topic**：`order-created`、`order-paid`，生产者按事件类型发不同 Topic。路由逻辑在生产者；
3. **Kafka Streams / Flink 做分流**：从主 Topic 读，按规则写到下游 Topic。灵活但多一层计算。

对比 RabbitMQ：**加一个队列 + 一条 binding 就完成**，生产者零改动。这就是「消息路由器」的价值。

## 二、延迟消息：RabbitMQ 的主场，Kafka 的荒地

### 2.1 RabbitMQ 的三种实现

**方案 A：队列 TTL + 死信**

```text
msg(TTL=30m) → queue.delay.30m（无消费者）→ 过期 → DLX → queue.order.close → 消费者
```

坑：**队列级 TTL 是队头阻塞的**。队头消息 30 分钟过期，后面 1 分钟过期的消息也得等队头先死。要精确，得**每个延迟档位一个队列**（1s/5s/30s/5m/30m）。

**方案 B：消息级 TTL + 死信**

每条消息带自己的 `expiration`。但 RabbitMQ 只检查**队头**的过期时间，仍然可能被前面的长延迟消息挡住。所以官方推荐 A 的「分档队列」而不是 B。

**方案 C：延迟插件 `rabbitmq_delayed_message_exchange`**

声明 `x-delayed-message` 类型的 Exchange，消息带 `x-delay` 头，插件内部定时投递。**精度好、用法简单**，是生产首选；注意它把延迟消息存在本地 Mnesia，量特别大时要评估。

### 2.2 Kafka 的替代方案

Kafka **没有原生延迟**。常见做法：

1. **多级延迟 Topic**：`delay-1s`、`delay-30s`、`delay-5m`，消费者到点后转发到真实 Topic。本质是自己实现时间轮；
2. **外部调度**：Redis ZSet（`score=到期时间`）+ 定时任务扫描，到点写回 Kafka；
3. **消费端过滤**：消息带 `deliverAt`，未到期就 `pause` 分区——**强烈不推荐**，会阻塞整个分区。

**Q：为什么 Kafka 不做延迟消息？**

延迟消息需要「按时间排序的随机插入」，而 Kafka 的存储是「按到达顺序追加」。要实现延迟，就得在 Broker 内维护额外的定时器与索引，破坏「日志」这一核心模型。社区的选择是：保持日志纯粹，把延迟留给上层。

## 三、失败重试与死信：原生 vs 自建

### 3.1 RabbitMQ：DLX 是标准件

```text
queue.order
  ├─ 消费失败 nack(requeue=false)
  └─ → DLX → queue.order.retry.5s（TTL=5s）→ DLX → queue.order
                                        └─ 超过次数 → queue.order.dlq
```

要点：

- 消息每死信一次，`x-death` 头会累加，可据此判断重试次数；
- **不要无条件 `requeue=true`**，否则毒消息无限循环；
- 重试队列本身也要设 `x-max-length`，防止雪崩时无限堆积。

### 3.2 Kafka：重试是应用层模式

业界标准做法是 **Retry Topic + DLQ**：

```text
order-topic → 消费失败（带 retryCount 头）
            ├─ retryCount < 3 → 发到 order-retry（延迟消费，按档位）
            └─ retryCount = 3 → 发到 order-dlq（人工/补偿任务）
```

坑：

- **重试 Topic 不能立即消费**，否则等于原地快速重试，打爆下游；要配合延迟（见上一节）；
- **重试会破坏顺序**：失败消息绕道期间，原分区的新消息继续被消费。要保序就得阻塞分区；
- Spring Kafka 的 `@RetryableTopic` 自动生成这套 Topic，但本质仍是上面的模式。

**Q：能不能直接不提交位点，等重试成功？**

可以，但会**卡住整个分区**（head-of-line blocking），后面的消息全部等着。适用于「必须严格有序且失败极少」的场景，不适合普通业务。

## 四、回溯与重放：Kafka 的结构性优势

| | Kafka | RabbitMQ（classic/quorum） | RabbitMQ Streams |
|---|---|---|---|
| 按时间回放 | 支持（reset offset） | 不支持 | 支持（按 offset/timestamp） |
| 新服务补历史 | 支持 | 不支持 | 支持 |
| 消费后数据 | 保留至过期 | 删除 | 保留至过期 |
| 典型用途 | 数仓重跑、CDC、审计 | — | 大吞吐多下游、可回放 |

Kafka 回放示例：

```bash
# 把消费组位点重置到 24 小时前（需要先停掉消费者）
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group order-service --reset-offsets \
  --to-datetime 2026-11-25T00:00:00.000 --topic order --execute
```

**Q：回放会不会导致重复副作用？**

会。回放意味着业务逻辑会再执行一遍，所以：发短信、扣款这类操作必须有幂等键（订单号 + 事件 ID），否则回放就是事故。**能回放的前提是消费逻辑可重入**。

## 五、堆积：谁扛得住，谁会被压垮

### 5.1 Kafka：积压是常态

Kafka 的消费进度与消息存储解耦，积压只表现为：

- 磁盘占用增加（写入速率 × 积压时长）；
- consumer lag 上涨；
- 页缓存命中率下降，读变慢。

只要磁盘够、保留期够，积压几亿条不是事故，是「等会儿再处理」。这也是它适合削峰的根本原因。

### 5.2 RabbitMQ：积压是告警

RabbitMQ 的队列索引在内存，积压会导致：

- 内存上涨 → 触发 `vm_memory_high_watermark` → **阻塞生产者**（连接 blocked）；
- 持久化消息写磁盘，但索引仍在内存；
- quorum 队列还要维持 Raft 日志，磁盘与内存双重压力。

缓解手段：

- **lazy queue**：消息尽量落盘，内存只留索引；
- `x-max-length` / `x-max-length-bytes`：主动丢弃或拒绝，防止无限堆积（要配合 DLX）；
- 监控 ready 数、unacked 数、内存与磁盘告警。

**Q：为什么「积压」在两者身上含义完全不同？**

因为**消费进度是否影响存储**。Kafka 的 offset 是客户端读数，消息按时间过期；RabbitMQ 的消息在 ack 后删除，积压直接等于「未被处理的消息集合」。前者是日志，后者是待办清单。

## 六、扩展：分区 vs 队列

| 维度 | Kafka | RabbitMQ |
|------|-------|----------|
| 扩容单位 | Partition（可迁移到新 Broker） | Queue（分散到不同节点） |
| 单流吞吐 | 随分区数线性扩展 | 单队列受单节点限制 |
| 加节点效果 | 迁移部分分区，整体吞吐提升 | 新队列可放新节点，老队列不变 |
| 元数据 | Controller/KRaft 管理，万级分区有压力 | 全量复制到所有节点，队列数多时开销大 |
| 上限 | 分区数（fd、恢复时间） | 队列数（Erlang 进程、内存） |

**Q：百万级 Topic/分区可行吗？**

Kafka 在 KRaft + 分层存储下可以做到很大规模，但每个分区仍有 fd、元数据、恢复成本。常规业务几千到几万分区足够。RabbitMQ 更怕「海量队列」：每个队列都是 Erlang 进程，几万个队列就开始吃力。

## 七、可观测性：各自该盯什么

| 指标 | Kafka | RabbitMQ |
|------|-------|----------|
| 堆积 | consumer lag（按组分分区） | ready messages、unacked |
| 健康 | ISR 缩水、UnderReplicatedPartitions、离线分区 | 节点存活、分区网络、队列 Leader |
| 流量 | 入/出字节、消息速率 | publish/deliver/ack 速率 |
| 资源 | 磁盘使用、页缓存、网络 | 内存水位、磁盘剩余、fd |
| 异常 | Controller 切换、rebalance 频率 | connection.blocked、flow control、死信速率 |

## 八、能力对照总表

| 能力 | Kafka | RabbitMQ | 结论 |
|------|-------|----------|------|
| 复杂路由 | 弱 | 强 | 按规则分发选 RabbitMQ |
| 延迟消息 | 无原生 | 插件/TTL+DLX | 延迟任务选 RabbitMQ |
| 失败重试/死信 | 需自建 | 原生 DLX | 业务重试选 RabbitMQ |
| 历史回放 | 强 | classic 不支持，streams 支持 | 回放/补数据选 Kafka |
| 海量积压 | 强 | 一般 | 削峰/离线管道选 Kafka |
| 水平扩展 | 强（分区） | 中（队列分散） | 超大流量选 Kafka |
| 多下游全量消费 | 强（消费组） | 需复制队列 | 多下游选 Kafka |
| 低延迟小消息 | 中 | 强 | 实时通知选 RabbitMQ |
