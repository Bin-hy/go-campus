# MySQL 锁机制全解 · Plan

## 架构概览

新增一篇独立长文，采用"**问题驱动 + 分层拆解 + 实测验证**"的结构，主问题贯穿全文：

> 一条 `UPDATE` 到底锁了什么？为什么你以为只锁一行，实际却锁住了一片？

全文分四个层次递进：

1. **为什么需要锁**：讲清锁与 MVCC 的分工，建立"锁只服务于写和当前读"的定位。
2. **有哪些锁**：按粒度从大到小——全局锁 → 表级锁（表锁 / MDL / AUTO-INC）→ 行级锁（S/X、意向锁、记录锁、间隙锁、临键锁、插入意向锁）。
3. **怎么推导锁范围**：加锁规则 + 索引/执行计划的影响 + `performance_schema.data_locks` 实测方法。
4. **锁的代价与使用**：死锁的成因、检测、排查、治理；悲观锁 vs 乐观锁的选型。

文章延续本系列风格：场景开头、口语化、表格与 SQL 片段并用、mermaid 图、结尾"串起来"+ 下一篇预告。

### 开篇（约 400 字）

用一个线上现象开场：两个事务明明改的是不同的行，却互相阻塞；或者 RR 下一个 `INSERT` 莫名卡住。抛出核心命题：

> **InnoDB 的行锁不是锁在"行"上，而是锁在"索引记录"上；你锁住的范围，由执行计划决定，而不是由 SQL 字面决定。**

声明全文路线：先讲清锁的分工和全景，再逐层拆到行锁，最后落到死锁与实战。

### 第 1 章：锁到底在保护什么（约 1000 字）

- 回顾隔离性：MVCC 让**快照读**无锁；但**写操作**和**当前读**必须看到并修改最新数据，只能靠锁串行化。
- 对照表：

  | 操作 | 读什么 | 是否加锁 | 靠什么 |
  |------|--------|----------|--------|
  | 普通 `SELECT` | 历史快照 | 不加锁 | MVCC |
  | `SELECT ... FOR SHARE` | 最新数据 | 加 S 锁 | 锁 |
  | `SELECT ... FOR UPDATE` | 最新数据 | 加 X 锁 | 锁 |
  | `UPDATE` / `DELETE` | 最新数据 | 加 X 锁 | 锁 |

- 讲清两个方向：为什么不能全靠锁（读写互相阻塞、吞吐差），为什么不能全靠 MVCC（写写冲突、当前读必须看到最新值）。
- 锁的代价：阻塞、死锁、检测开销——为后文埋线。

### 第 2 章：锁的全景图（约 1200 字）

- 四个分类维度：
  1. 按粒度：全局锁 → 表级锁 → 行级锁
  2. 按模式：共享 S / 排他 X
  3. 按实现层：Server 层（全局锁、MDL、`LOCK TABLES`）vs InnoDB 引擎层（行锁、意向锁、AUTO-INC）
  4. 按思想：悲观锁（数据库锁）vs 乐观锁（应用层版本号/CAS）
- **mermaid 图 1**：锁体系全景树。
- 表格：每类锁一句话定位 + 本文对应小节。
- 强调：日常说的"MySQL 锁"90% 指 InnoDB 行锁，但真正把线上打挂的往往是全局锁和 MDL。

### 第 3 章：全局锁与表级锁（约 2800 字）

#### 3.1 全局锁 FTWRL（约 600 字）

- `FLUSH TABLES WITH READ LOCK`：整库只读，写和 DDL 全阻塞，SELECT 可读。
- 用途：全库逻辑备份拿一致性快照。
- 为什么很少用：备份期间业务写全停；主库上尤其危险。
- 替代方案 `mysqldump --single-transaction`：用 RR + 一致性视图在事务里备份，不阻塞写。
- **知其所以然**：备份要的是"同一时刻的一致性视图"，MVCC 能给，就不必把整库锁死；MyISAM 不支持事务，才不得不 FTWRL。

#### 3.2 表锁 `LOCK TABLES`（约 400 字）

- `LOCK TABLES t READ / WRITE`：读锁共享、写锁排他；会限制当前会话只能访问被锁表。
- MyISAM 时代的主力，InnoDB 下与事务配合差、一般不推荐。
- 区分：这是**显式**表锁；InnoDB 还有**隐式**的表级意向锁（4.2 讲）。

#### 3.3 MDL 元数据锁（约 1100 字）

- 5.5 引入，**自动加、无法关闭**，用于保护表结构不被并发 DDL 改掉。
- 规则：DML（增删改查）加 MDL 读锁（共享）；DDL 加 MDL 写锁（排他）；读读兼容，读写/写写冲突。
- 关键机制：**事务内 MDL 读锁一直持有到事务提交**，不是语句结束就释放。
- 经典雪崩链条（mermaid 图 2 或文字时序）：
  1. 长事务 A 持有 MDL 读锁且迟迟不提交；
  2. B 的 `ALTER TABLE` 申请 MDL 写锁，被 A 挡住，进入等待；
  3. 后续所有新查询申请 MDL 读锁，排在 B 后面（避免写锁饿死）；
  4. 连接池被排队的请求占满 → 整张表不可用。
- 强调："DDL 把线上打挂"通常不是 DDL 本身慢，而是**它前面有个没提交的长事务，后面堵了一串普通查询**。
- 排查：`SHOW PROCESSLIST` 找 `Waiting for table metadata lock`；`performance_schema.metadata_locks`；`sys.schema_table_lock_waits`。
- 治理：DDL 前查长事务；设置 `lock_wait_timeout`；大表用 `gh-ost` / `pt-online-schema-change`；8.0 online DDL 仍需短暂 MDL 排他，不能免疫长事务。

#### 3.4 AUTO-INC 锁（约 700 字）

- 自增列分配必须不重复且递增，并发 INSERT 要串行拿号。
- 三种 `innodb_autoinc_lock_mode` 对照表：

  | 模式 | 行为 | 自增值 | 并发 |
  |------|------|--------|------|
  | 0 传统 | 语句级 AUTO-INC 表锁 | 连续 | 最差 |
  | 1 连续 | 简单插入用轻量互斥量批量分配；批量插入用表锁 | 基本连续 | 中等 |
  | 2 交错（8.0 默认） | 全用轻量互斥量 | 可能有空洞 | 最好 |

- **知其所以然**：8.0 默认 2，是因为 binlog 默认 ROW，不再依赖语句级自增值连续；用"可能不连续"换并发。
- 指出 AUTO-INC 锁锁的是**计数器**，不是数据行，别和行锁混为一谈。

### 第 4 章：InnoDB 行级锁（约 4500 字）

#### 4.1 总纲：行锁加在索引上（约 500 字）

- 先立命题：InnoDB 的行锁是加在**索引记录**上的；没有可用索引时，全表扫描会把遇到的每条记录和每个间隙都锁住，效果等同锁表。
- 澄清一个常见误传：InnoDB **不会**主动把行锁升级成表锁；"像表锁"是无索引导致的锁范围扩大。
- 30 秒复习聚簇索引/二级索引/回表（因为本篇在《索引与 SQL 优化》之前），并给出指向下一篇的链接。

#### 4.2 共享锁与排他锁（约 600 字）

- S 锁 / X 锁定义；兼容矩阵：

  | 已持有 \ 请求 | S | X |
  |---------------|---|---|
  | S | 兼容 | 冲突 |
  | X | 冲突 | 冲突 |

- SQL 写法：`FOR SHARE`（8.0）/ `LOCK IN SHARE MODE`（5.7）加 S；`FOR UPDATE`、`UPDATE`、`DELETE` 加 X。
- 附带 `NOWAIT` / `SKIP LOCKED`（8.0）的实用场景（任务队列抢单）。
- **知其所以然**：普通 SELECT 为什么不加 S 锁——因为 MVCC 已经保证读到一致快照，加 S 锁只会白白增加冲突。

#### 4.3 意向锁 IS / IX（约 800 字）

- 问题：事务想给整表加锁时，要判断"有没有行被锁"，逐行检查太慢。
- 方案：加行锁前先在表级加一个"意向锁"路标；表锁只需看意向锁即可。
  - 要在某行加 S 锁 → 先加 IS；
  - 要在某行加 X 锁 → 先加 IX。
- 兼容矩阵（IS/IX 之间全部兼容，只是路标）：

  | 已持有 \ 请求 | IS | IX | 表 S | 表 X |
  |--------------|----|----|------|------|
  | IS | 兼容 | 兼容 | 兼容 | 冲突 |
  | IX | 兼容 | 兼容 | 冲突 | 冲突 |

- **知其所以然**：意向锁之间不冲突，也不和行锁冲突，它唯一的作用是让表级锁判断 O(1) 完成。

#### 4.4 记录锁 / 间隙锁 / 临键锁（约 1800 字）

- **记录锁 Record Lock**：锁单条索引记录。
- **间隙锁 Gap Lock**：锁开区间 `(a, b)`，锁的是"不存在的空间"，目的是阻止插入；间隙锁之间互相兼容。
- **临键锁 Next-Key Lock**：记录锁 + 前面的间隙 = 左开右闭 `(a, b]`，是 RR 下默认的加锁单位。
- 为什么 RR 需要间隙/临键锁：当前读要防幻读，光锁已有记录挡不住 INSERT。
- 为什么 RC 基本不用间隙锁：RC 允许当前读看到新提交数据，用"更少的锁"换并发；代价是当前读仍可能幻读。
- **ASCII 图**：用示例表的索引记录画出 `(-∞,5] (5,10] (10,15] (15,20] (20,25] (25,+∞)` 的分段。
- 强调：间隙锁可能锁住"你查询里根本没出现"的值，这是很多"莫名阻塞"的根源。

#### 4.5 插入意向锁（约 800 字）

- `INSERT` 执行前，会先在目标间隙上加**插入意向锁**（一种特殊的间隙锁），表示"我准备往这里插"。
- 兼容规则：多个插入意向锁之间**互相兼容**（只要插入位置不同就能并发插）；插入意向锁与间隙锁/临键锁**冲突**。
- **知其所以然**：这就是"间隙被锁后 INSERT 会被阻塞"的底层原因；也是间隙锁死锁的常见来源。
- 给出两个事务各持间隙锁、再互相插入造成死锁的示意（与第 6 章呼应）。

### 第 5 章：一条 SQL 到底加什么锁（约 3000 字）

#### 5.1 统一示例表（约 300 字）

```sql
CREATE TABLE t (
  id INT PRIMARY KEY,
  c  INT,
  d  INT,
  KEY idx_c (c)
) ENGINE=InnoDB;

INSERT INTO t VALUES (5,5,5),(10,10,10),(15,15,15),(20,20,20),(25,25,25);
```

说明：`id` 是唯一主键，`c` 是普通二级索引，`d` 无索引。

#### 5.2 五类场景速查表（约 700 字）

| SQL 形态 | 用到的索引 | 加锁结论 |
|----------|-----------|----------|
| `WHERE id = 10 FOR UPDATE` | 唯一索引等值**命中** | 记录锁，只锁 `id=10` |
| `WHERE id = 7 FOR UPDATE` | 唯一索引等值**未命中** | 间隙锁 `(5,10)` |
| `WHERE c = 10 FOR UPDATE` | 普通索引等值 | 临键锁 `(5,10]` + 间隙锁 `(10,15)` + 主键记录 |
| 范围查询（如 `id > 10 AND id <= 15`） | 唯一/普通索引范围 | 临键锁覆盖扫描区间，可能多扫一格 |
| `WHERE d = 10 FOR UPDATE` | **无索引** | 全表所有记录 + 所有间隙，等效锁表 |

#### 5.3 完整推演：为什么 `WHERE c = 10` 锁了 `(5,15)`（约 1200 字）

逐步推演，每一步说明 InnoDB 在做什么、为什么：

1. 从 `idx_c` 找到 `c=10` 的记录，加临键锁 `(5,10]`（含记录 + 前面的间隙）。
2. 因为 `c` 不唯一，无法确认后面还有没有 `c=10`，必须继续向右扫到 `c=15`。
3. `c=15` 不满足等值条件，它的临键锁退化为间隙锁 `(10,15)`。
4. 锁定读要回表，聚簇索引上 `id=10` 的记录也加锁。

结论：`(5,15)` 这段区间都插不进 `c=5~15` 的新值——**你只查了 `c=10`，却锁住了一整段**。

- 配 ASCII 图：`idx_c` 区间和锁覆盖范围高亮。
- 对照 RC：同样 SQL 只锁 `c=10` 记录和主键记录，不锁间隙，插入不阻塞。

#### 5.4 五条加锁规则（约 500 字）

提炼成可迁移的规则：

1. 加锁基本单位是临键锁，区间左开右闭。
2. 只有扫描过程中**访问到**的索引记录/范围才会加锁。
3. 唯一索引等值命中 → 临键锁退化为记录锁（唯一性保证不会插重复值，不必锁间隙）。
4. 等值查询向右扫到第一个不满足条件的记录时，其临键锁退化为间隙锁。
5. 范围查询会扫到第一个不满足条件的记录为止，锁范围可能比字面范围大。

#### 5.5 别背结论，自己实测（约 300 字）

- 给出一段可复制的 SQL：开事务执行 `FOR UPDATE`，另开会话查：

```sql
SELECT ENGINE_TRANSACTION_ID, INDEX_NAME, LOCK_TYPE, LOCK_MODE,
       LOCK_DATA, LOCK_STATUS
FROM performance_schema.data_locks
WHERE OBJECT_SCHEMA = DATABASE() AND OBJECT_NAME = 't';
```

- 说明各列含义（`LOCK_MODE` 区分 `X,REC_NOT_GAP` / `X,GAP` / `X` 临键锁）。
- 5.7 用 `information_schema.innodb_locks`。
- 观点：加锁规则细节多、版本有差异，**实测比背诵可靠**。

### 第 6 章：索引决定锁的边界（约 1800 字）

- 三个真实感的坑：
  1. **隐式类型转换**：`phone` 是 varchar，`WHERE phone = 13800138000` 导致索引失效 → 本该锁一行变成锁全表。
  2. **对索引列用函数**：`WHERE DATE(create_time) = '2024-01-01'` 同理。
  3. **优化器选错索引**：你以为锁主键，实际走了另一个索引，锁范围完全不同。
- 二级索引回表加锁：锁二级索引记录时，聚簇索引对应记录也会被锁。
- 实践三原则：`UPDATE`/`DELETE` 必须走索引；优先主键/唯一索引等值；上线前 `EXPLAIN` 确认 `key`，并对关键语句用 `data_locks` 实测。
- 呼应开篇：这就是"一条 UPDATE 锁了什么"的最终答案——**锁的范围 = 执行计划访问到的索引记录 + 间隙**。
- 实践提醒：大事务 = 长持锁，拆小；热点行更新用单语句原子更新（`UPDATE ... WHERE stock > 0`），避免"先查后改"放大锁窗口。

### 第 7 章：死锁（约 2500 字）

#### 7.1 死锁是怎么形成的（约 500 字）

- 四个必要条件：互斥、请求并保持、不可剥夺、循环等待。
- mermaid 图 3：A 持 id=1 等 id=2，B 持 id=2 等 id=1，形成环。

#### 7.2 InnoDB 怎么处理死锁（约 700 字）

- `innodb_deadlock_detect`（默认 ON）：用 **wait-for graph** 检测环，发现后回滚"代价较小"的事务（修改/锁定行数少者），报错 1213。
- 检测成本：每次加锁都可能遍历等待图，并发高时是 O(n) 的 CPU 开销。
- 与 `innodb_lock_wait_timeout`（默认 50s）的区别：死锁是主动检测立即回滚；超时是等不到锁被动放弃。
- 关闭死锁检测的取舍：CPU 降下来，但冲突只能靠超时兜底，响应变慢。

#### 7.3 三类经典死锁（约 700 字）

1. **交叉更新**：两个事务以相反顺序更新两行——固定顺序可解。
2. **间隙锁 + 插入意向锁**：两个事务各锁一段间隙，再各自往对方间隙插入——RR 下高频，缩小锁范围或改 RC 可缓解。
3. **唯一键冲突并发插入**：两个事务同时插同一个唯一键，互相等待对方释放 S 锁。

#### 7.4 排查与治理（约 600 字）

- 排查命令：
  - `SHOW ENGINE INNODB STATUS` → `LATEST DETECTED DEADLOCK`，看两个事务的 SQL、持锁、等锁。
  - `performance_schema.data_locks` / `data_lock_waits`、`sys.innodb_lock_waits`。
  - `innodb_print_all_deadlocks = ON`：把所有死锁写入错误日志。
- 治理清单：固定访问顺序、事务尽量短、走索引缩小锁范围、RC + ROW binlog、应用层捕获 1213 重试、热点行拆分/排队。
- 引用实验 `code/backend/01-mysql/04_deadlock` 和 `07_gap_lock`（给出相对路径与 README 指引）。

### 第 8 章：业务里怎么用锁（约 1200 字）

- **悲观锁**：`SELECT ... FOR UPDATE` 先锁再改，适合冲突多、强一致（扣库存、转账）。
- **乐观锁**：`UPDATE ... SET v = v + 1, version = version + 1 WHERE id = ? AND version = ?`，靠版本号/CAS，适合冲突少、读多写少；失败要重试。
- 对比表：加锁时机、冲突处理、并发度、适用场景、失败代价。
- 补充：扣库存优先用单条原子更新 `UPDATE ... WHERE stock >= n`，不必先 `SELECT` 再 `UPDATE`；`SKIP LOCKED` 适合队列型抢任务。
- 一句话带过分布式锁（不属于本文范围，指向 Redis 篇）。

### 结尾：把这条线串起来（约 600 字）

- 回答开篇问题：一条 UPDATE 锁的是**执行计划访问到的索引记录及其间隙**。
- 三层收口：全局锁/MDL 保护的是"库/表结构"；行锁保护的是"记录和间隙"；MVCC 保护的是"读的一致性"。
- 一句速记表：锁类型 → 一句话记忆点。

## 技术决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 文章位置 | 插在《事务与 MVCC》与《索引与 SQL 优化》之间 | 紧接 MVCC 的 next-key lock 伏笔；索引作为"锁范围决定因素"在下一篇继续深化。为弥补索引前置知识，第 4.1 节加 30 秒复习 |
| 叙述主线 | 以"一条 UPDATE 锁了什么"贯穿 | 问题驱动比分类罗列更易记，也直接对应线上困惑 |
| 加锁规则讲法 | 规则 + 实测方法并重 | 规则细节多、版本有差异，教读者用 `data_locks` 验证比要求死记更可靠 |
| 示例表 | 沿用经典 `t(id, c, d)` + `(5,10,15,20,25)` 数据 | 读者可对照公开资料复现，便于自测 |
| 版本口径 | 以 8.0 为准，标注 5.7 差异 | 与团队/面试主流环境一致 |
| 实验引用 | 只引用 `04_deadlock` / `07_gap_lock`，不新增代码 | 用户已确认；避免本文变成代码教程 |
| 深度取舍 | 不深入 MyISAM 表锁、Redis 分布式锁 | 与 S1 主题无关，避免发散 |
| 图表形式 | mermaid 3 张 + ASCII 1 张 + 表格 6 张 | 遵循 CLAUDE.md "流程图用 mermaid" 约定，兼顾 VitePress 渲染 |

## 术语与口径（写作时统一）

- 统一用"临键锁（next-key lock）"，首次出现标注英文。
- `SELECT ... FOR SHARE` 为主，括号注明 5.7 的 `LOCK IN SHARE MODE`。
- "当前读"= 锁定读 + `UPDATE`/`DELETE`；"快照读"= 普通 `SELECT`。
- `performance_schema.data_locks` 为主，5.7 的 `information_schema.innodb_locks` 用一句话标注。
- 不自造术语；"锁升级"只用于澄清"InnoDB 不会主动升级行锁"。
