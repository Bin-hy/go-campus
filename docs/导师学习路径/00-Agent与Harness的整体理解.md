# 00 · Agent 与 Harness 的整体理解

## 一、Agent = LLM + Harness：应用开发主要在做什么

对于应用层 Agent，可以先建立两个核心认识：

1. **Agent 由 LLM 和围绕 LLM 的外部程序组成。这套外部程序就是 Harness，也是 AI 应用开发的主要对象。**
2. **与 LLM 对接时，重点是实现通信，以及通过 Harness 的请求组织提高 KV Cache 的复用机会。**

本篇按这两个重点展开，再比较不同 Agent 形态，并说明为什么以 Coding Agent 作为主要开发对象。

$$
\boxed{\text{Agent System} \approx \text{LLM} + \text{Harness}}
$$

LLM 根据当前输入生成回答、计划或行动建议；Harness 是围绕模型组织上下文、工具执行、状态和控制规则的外部程序。

这里把 Agent 应用中围绕模型的通信、工具接入、上下文、状态和运行控制统称为 Harness；操作系统、数据库等是它接入的环境。这个公式用来划分工程职责。

更具体地展开：

$$
\text{Harness} \approx \text{Loop} + \text{Context} + \text{Tools Integration} + \text{State} + \text{Control}
$$

| 组成 | 负责的问题 | Coding Agent 中的例子 |
| --- | --- | --- |
| LLM | 当前信息下，下一步应该输出什么？ | 建议先读测试，再检查目标函数 |
| Loop | 如何继续、暂停或结束一次任务？ | 工具执行后再次调用模型 |
| Context | 本次模型调用需要看到什么？ | 用户目标、相关代码、测试输出、项目规则 |
| Tools Integration | 如何把调用意图接到真实能力？ | 将 `read_file` 分派给文件读取实现 |
| State | 任务实际上进行到了哪里？ | 当前步骤、已修改文件、待确认操作 |
| Control | 哪些动作允许执行，资源如何限制？ | 路径权限、超时、最大步数、费用预算 |

**模型输出提供决策信息，程序负责把经过检查的决策落实到环境，并收集真实结果。**

Claude Code 的官方说明也将工具、上下文管理和执行环境归入围绕模型的 agentic harness。[Claude Code 工作机制](https://code.claude.com/docs/en/how-claude-code-works)

## 二、与 LLM 对接的两个重点：通信与缓存复用

对于调用已有模型 API 的应用，开发者通常不修改模型权重。Harness 一方面把输入送给模型、接收输出，另一方面组织可复用的请求前缀，减少多轮调用中的重复输入计算。

### 2.1 实现 LLM 通信

$$
\text{Harness} \xrightarrow{\text{Request}} \text{LLM}
\xrightarrow{\text{Response}} \text{Harness}
$$

| 环节 | Harness 实现的工作 |
| --- | --- |
| 准备输入 | 组装指令、用户目标、历史消息、相关资料和工具描述 |
| 发送请求 | 使用 HTTP / SDK 调用模型，设置模型与输出参数 |
| 接收响应 | 解析文本、工具调用及结束原因，聚合流式事件 |
| 处理异常 | 管理超时和重试，记录用量、延迟与错误 |

因此，可以把学习任务拆成：

$$
\text{Agent Engineering} \approx \text{LLM I/O} + \text{Harness 的其他工程}
$$

**LLM I/O 也是 Harness 的组成部分。** 单独列出，是为了区分模型通信与其他运行逻辑。

### 2.2 通过 Harness 提高 KV Cache 复用机会

**KV Cache 保存的是模型处理历史 token 时计算出的 Key / Value 张量。** 在同一次生成中，它让后续 token 可以使用已算出的历史 K/V；推理服务如果支持跨请求前缀缓存，还可以在后续请求中复用相同输入前缀的 K/V，减少输入处理（Prefill）的重复计算。[vLLM 前缀缓存说明](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)

在多轮 Agent 中，这很有价值：模型读完文件后要再调用一次，运行测试后还要再调用一次，前面的规则、工具定义和历史消息往往会反复出现在请求中。

下面用简化的输入序列说明；实际 API 的字段和排列由服务协议决定：

```text
第 1 次：固定规则 | 固定工具定义 | 用户任务
第 2 次：固定规则 | 固定工具定义 | 用户任务 | 模型工具调用 | 读取文件结果
第 3 次：固定规则 | 固定工具定义 | 用户任务 | 模型工具调用 | 读取文件结果 | 新调用与结果
        └────────────── 保持不变的前缀 ──────────────┘
```

后一次请求保留前一次的输入前缀，并在尾部追加新信息。**支持前缀缓存的推理服务，就有机会复用此前计算过的部分。** “意思差不多”不足以复用：服务端实际处理的前缀需要满足其匹配规则。Claude 的 Prompt Caching 也要求缓存段完全相同，并按照 `tools → system → messages` 的顺序构建前缀。[Claude Prompt Caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

| Harness 的做法 | 为什么有利于复用 |
| --- | --- |
| 将可复用的规则、示例和资料放在稳定的前缀中 | 多次请求可以共享已处理的输入 |
| 保持工具定义、排列和序列化结果稳定 | 避免无意义的格式变化改动前缀 |
| 将本轮变化的信息放在后面，并按协议追加新消息 | 保留此前请求中仍然有效的内容 |
| 避免在开头反复插入时间戳、随机 ID 或改写旧消息 | 避免过早打断共同前缀 |
| 按模型服务要求启用缓存或设置缓存边界 | 让稳定前缀能够被服务端实际缓存 |

**Harness 组织输入，推理服务保存并复用缓存。** 实际命中受缓存有效期、长度要求和可共享范围影响。可通过缓存读取 token 占总输入 token 的比例、首 token 延迟和费用比较优化效果；前缀缓存主要减少 Prefill 工作，新输出仍需要生成。[vLLM 前缀缓存说明](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)

需要压缩上下文或更新工具时，应正常调整请求。任务正确性优先于缓存命中；KV Cache 保存计算结果，业务记忆和任务状态仍由 Harness 维护。推理引擎内部的缓存管理见 [08 LLM 推理优化](./08-JD专题-LLM推理优化)。

## 三、不同 Agent 形态与 Coding Agent 的开发价值

很多 Agent 可以用相似的决策—执行—反馈循环组织，但环境、动作和验收方式差别很大。

| 形态 | 环境 | 典型工具 | 完成证据示例 |
| :--- | :--- | :--- | :--- |
| Coding Agent | 代码仓库、Shell | 查找、读取、编辑、运行测试 | 修改结果与相关测试 |
| Research Agent | 网页、文献和资料库 | 搜索、读取、检索、比较 | 可追溯来源与问题覆盖情况 |
| Browser Agent | 浏览器页面 | 点击、输入、读取页面 | 页面状态或服务端确认 |
| 视频处理 Agent | 素材、任务系统、处理服务 | 检索素材、提交处理、查询状态 | 可访问的成品和处理状态 |
| 个人事务 Agent | 邮箱、日历和业务账户 | 查询、草拟、提交 | 授权范围内的操作确认 |

不同形态主要改变了 **Harness 接入的环境、提供的工具，以及任务完成的判断方法**。写文件、点击提交和发送邮件的副作用不同，权限和失败处理也要分别设计。

### 为什么本项目以 Coding Agent 为主要开发对象

1. **环境熟悉，容易从小任务开始。** 本项目围绕 Go 与后端工程学习，可以用已有仓库练习查找函数、修复一个错误、补齐一个功能，直接观察模型如何使用代码上下文。
2. **反馈具体，便于验证。** 文件差异、编译错误和测试结果能成为下一轮输入，也能提供验收证据。测试通过后，仍要检查修改是否满足需求、测试是否覆盖关键行为。
3. **能覆盖 Harness 的主要工程能力。** 一个修复任务就会涉及模型通信、工具调用、上下文管理、循环、权限、超时和状态记录；多轮请求也适合观察前缀缓存的复用效果。
4. **便于控制实验范围并迁移经验。** 可以在独立工作目录中限制文件与命令权限，用 Git 检查和撤销受控的代码修改；学到的工具调度、反馈处理和状态管理，再迁移到研究、浏览器或视频任务。命令产生的外部副作用需要另外管理。

例如，任务是“修复一个 Go 函数的边界条件”：模型提出读取或修改操作，Harness 校验参数与权限，调用真实文件工具，再将结果送回模型；运行相关测试后，根据反馈继续修复或提交结果。

**工具 Schema 只是给模型看的接口说明，真实执行仍需 Harness 接到工具实现。任务完成则需要修改结果与验收证据。** 这让 Coding Agent 成为学习“模型如何接入一个能实际执行的软件系统”的具体练习对象。
